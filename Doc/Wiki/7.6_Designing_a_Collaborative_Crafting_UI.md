# 7.6. 협력 제작 UI 설계

> ### 협력 제작을 위한 역할 기반 UI 아키텍처
> 
> *   **역할 기반 UI 분리:** 제작대와 상호작용하는 UI를 '초대장'(`DetectWidget`), '개인 제어판'(`CraftingWidget`), '공개 정보 게시판'(`CraftingQueueWidget`)이라는 세 가지 역할로 명확히 분리했습니다.
> *   **정보의 성격에 따른 분리:** 모든 플레이어가 봐야 할 **공개 정보**(제작 진행률)와, 제작자만 봐야 할 **개인 정보**(레시피 목록, 재료)를 각기 다른 위젯이 책임지도록 하여, 협력 플레이의 기반을 마련했습니다.
> *   **선택적/이벤트 기반 갱신:** 레시피를 선택할 때 UI 전체를 새로 그리는 대신, 정적/동적 데이터를 구분하여 변경이 필요한 부분만 갱신하고, 플레이어 인벤토리의 변화는 이벤트를 구독하여 실시간으로 반영합니다.

## 7.6.1. 구현 기능 목록 (Feature List)

*   **컨텍스트 기반 상호작용 안내:** 제작대의 현재 상태(대기, 제작 중, 완료)에 따라, 플레이어가 다음에 할 수 있는 행동("레시피 선택", "작업 돕기", "취득")을 안내하는 UI가 표시됩니다.
*   **실시간 재료 확인:** 제작 UI에서 제작할 아이템을 선택하면, 필요한 재료와 현재 플레이어가 보유한 재료의 수량이 실시간으로 표시됩니다. 재료가 부족할 경우 해당 항목이 붉게 표시됩니다.
*   **제작 진행 상황 공유:** 제작이 시작되면, 제작대 주변의 모든 플레이어는 현재 제작 중인 아이템의 아이콘과 남은 시간을 실시간으로 확인할 수 있습니다.
*   **효율적인 UI 갱신:** 수십 개의 재료가 필요한 복잡한 레시피를 선택하거나 제작 수량을 조절해도, UI의 끊김 없이 즉각적으로 정보가 갱신됩니다.

---

## 7.6.2. 기술 상세 (Technical Deep Dive)

### 7.6.2.1. 설계 목표

1.  **명확한 역할 분담:** 모든 플레이어가 보는 **공개 정보**(제작 큐)와 제작자 한 명만 보는 **개인 정보**(레시피 목록)를 UI 레벨에서 명확히 분리하여 혼동 없는 협력 플레이 경험을 제공하는 것을 목표로 합니다.
2.  **UI 반응성 극대화:** 복잡한 레시피를 선택하거나 제작 수량을 조절해도 UI가 즉각적으로 반응하도록, 변경이 필요한 위젯만 선택적으로 갱신하는 고성능 구조를 목표로 합니다.
3.  **느슨한 결합:** 각 UI 위젯이 데이터 소스(`ACraftingStation`)의 상태 변화에 이벤트 기반으로 독립적으로 반응하도록 하여, UI 간의 직접적인 의존성을 최소화하고 확장성을 확보하는 것을 목표로 합니다.

### 7.6.2.2. 아키텍처: 세 위젯의 협력

제작 기능은 단순히 하나의 UI 창으로 이루어지지 않습니다. 플레이어의 상황과 역할에 따라 각기 다른 정보를 제공하는 여러 UI 위젯들의 유기적인 협력으로 완성됩니다. 제작 기능은 `DetectWidget`, `CraftingWidget`, `CraftingQueueWidget`이라는 세 가지 핵심 위젯이 `ACraftingStation`이라는 단일 데이터 소스를 중심으로 협력하는 구조입니다.

*   **`DetectWidget` (초대장):** 플레이어가 제작대를 바라볼 때, `ACraftingStation`의 상태에 따라 "레시피 선택", "작업 돕기" 등 컨텍스트에 맞는 텍스트를 표시하여 상호작용을 유도합니다. ([[7.4 확장 가능한 컨텍스트 UI|7.4_Scalable_Contextual_UI]])
*   **`CraftingWidget` (개인 제어판):** 제작을 시작한 플레이어 **한 명에게만** 보이는 개인 UI입니다. 제작 가능한 레시피 목록을 보여주고, 재료를 확인하며, 실제 제작을 시작하도록 서버에 요청하는 핵심적인 역할을 합니다.
*   **`CraftingQueueWidget` (공개 정보 게시판):** 제작대 주변의 **모든 플레이어**에게 보이는 공유 UI입니다. 현재 제작 중인 아이템, 남은 시간 등 공개적인 진행 상황을 실시간으로 표시합니다.

### 7.6.2.3. 핵심 구현

#### 7.6.2.3.1. `CraftingWidget`: 최적화와 실시간 반응성을 모두 잡다

`UCraftingWidget`은 제작 UI의 핵심으로, 복잡한 정보를 다루면서도 높은 반응성을 유지하기 위해 여러 기법이 적용되었습니다.

**1. UI 갱신 전략: 선택적 갱신과 오브젝트 풀링**

*   **초기화 시의 시각적 피드백:** 위젯이 처음 열릴 때, 제작 불가능한 레시피는 재료가 부족함을 미리 알려주기 위해 반투명하고 붉은 틴트를 적용하는 섬세한 UX를 제공합니다.
*   **정적/동적 데이터 분리:** 플레이어가 레시피를 선택하면, UI의 모든 것을 새로 그리는 대신, 레시피 자체가 바뀔 때만 갱신되는 **정적 정보**(아이템 이름, 재료 목록 레이아웃)와, 제작 수량 조절 등 빈번한 변경에 따라 항상 갱신되는 **동적 정보**(필요/보유 재료 수량, 제작 버튼 활성화)를 분리하여 처리합니다.
*   **위젯 오브젝트 풀링:** 재료 목록을 표시할 때는 위젯을 매번 생성/파괴하지 않고, 미리 만들어 둔 풀에서 재활용하는 **오브젝트 풀링**을 적용하여 성능 부하를 원천적으로 방지합니다. ([[7.3 UI 최적화: 오브젝트 풀링|7.3_Optimizing_UI_with_Object_Pooling]])

**2. 실시간 데이터 연동: 이벤트 기반 아키텍처의 일관된 적용**

*   **문제 상황:** 만약 플레이어가 제작 UI를 열어둔 상태에서 월드의 다른 아이템을 주워 재료의 개수가 변경되었다면, UI는 이 변경을 즉시 감지하고 '보유 수량' 텍스트와 '제작 가능' 여부를 다시 계산해야 합니다.
*   **해결 방안:** 이 문제를 해결하기 위해, `Tick`으로 매 프레임 검사하는 비효율적인 방식 대신, [[7.1 이벤트 기반 UI 아키텍처|프로젝트의 핵심 아키텍처]]를 일관되게 사용합니다. `CraftingWidget`은 `InventoryComponent`의 `OnInventoryChanged` 델리게이트를 구독하여, 데이터 변경 통지를 받았을 때만 UI를 갱신합니다.

    1.  **구독 (Subscribe):** 위젯이 초기화될 때(`Initialise`), 플레이어의 `InventoryComponent`에 접근하여 `OnInventoryChanged` 델리게이트에 자신의 `UpdateInventoryFromData` 함수를 등록합니다.
        ```cpp
        // In UCraftingWidget::Initialise
        if (InventoryComp)
        {
            InventoryComp->OnInventoryChanged.AddDynamic(this, &UCraftingWidget::UpdateInventoryFromData);
        }
        ```
    2.  **처리 (Handle):** `InventoryComponent`의 내용이 변경되어 이벤트가 발생하면, `UpdateInventoryFromData` 함수가 자동으로 호출됩니다. 이 함수는 UI 전체를 새로 그리는 대신, 이미 최적화된 `RefreshDetail` 함수를 호출하여 변경이 필요한 부분만 효율적으로 갱신합니다.
        ```cpp
        // In UCraftingWidget.cpp
        void UCraftingWidget::UpdateInventoryFromData(const TArray<FInventoryItem>& InventoryData)
        {
            RefreshDetail();
        }
        ```
    3.  **구독 해제 (Unsubscribe):** 위젯이 파괴될 때(`NativeDestruct`), 델리게이트 구독을 해제하여 메모리 누수나 충돌을 방지합니다.
        ```cpp
        // In UCraftingWidget::NativeDestruct
        if (InventoryComp)
        {
            InventoryComp->OnInventoryChanged.RemoveDynamic(this, &UCraftingWidget::UpdateInventoryFromData);
        }
        Super::NativeDestruct();
        ```
이 설계를 통해, `CraftingWidget`은 "언제 인벤토리가 변하는가"를 전혀 신경 쓸 필요 없이, 오직 "인벤토리가 변했다고 통보받으면 무엇을 할 것인가"에만 집중할 수 있습니다.

#### 7.6.2.3.2. `CraftingQueueWidget`의 이벤트 기반 공유

`CraftingQueueWidget`은 제작대 주변의 모든 플레이어에게 제작 진행 상황을 공유하는 역할을 합니다. 이는 [[7.1 이벤트 기반 UI 아키텍처|이벤트 기반 아키텍처]]를 통해 구현됩니다.

1.  **이벤트 구독 (Subscribe):** `CraftingQueueWidget`이 초기화될 때, 데이터 소스인 `ACraftingStation`의 `OnWorkChanged` 델리게이트에 자신의 `Refresh` 함수를 등록합니다.

```cpp
// Source/Sonheim/UI/Widget/GameObject/Crafting/CraftingQueueWidget.cpp
void UCraftingQueueWidget::Initialise(ACraftingStation* InStation)
{
    // ...
    if (Station)
    {
        Station->OnWorkChanged.AddUObject(this, &UCraftingQueueWidget::Refresh);
        Station->OnCompletedChanged.AddUObject(this, &UCraftingQueueWidget::Refresh);
    }
    // ...
}
```

2.  **이벤트 처리 (Handle):** 서버에서 제작이 진행되어 `ACraftingStation`의 `ActiveWork` 데이터가 변경되면, 이 데이터는 모든 클라이언트에 복제됩니다. 복제가 완료되면 `OnRep_ActiveWork` 함수가 호출되고, 이 함수는 `OnWorkChanged` 델리게이트를 방송합니다. 이 신호를 받은 모든 클라이언트의 `CraftingQueueWidget`들은 각자 자신의 `Refresh` 함수를 실행하여, 진행률 바와 텍스트를 동시에 업데이트합니다.

```cpp
// Source/Sonheim/GameObject/Buildings/Crafting/CraftingStation.cpp
void ACraftingStation::OnRep_ActiveWork()
{
	OnWorkChanged.Broadcast();
}
```

### 7.6.2.4. 회고: 왜 UI를 세 개로 분리했는가?

제작 UI를 하나의 거대한 위젯으로 만들 수도 있었지만, 역할을 기준으로 세 개의 위젯으로 분리한 이유는 **정보의 성격과 대상**이 각기 다르기 때문입니다. `DetectWidget`은 **불특정 다수**에게 **간단한 상호작용**을 유도하고, `CraftingWidget`은 **오직 한 명**에게 **복잡하고 개인적인 정보**를 제공하며, `CraftingQueueWidget`은 **특정 다수**에게 **단순하고 공개적인 정보**를 공유합니다. 이처럼 각기 다른 역할과 정보의 성격에 맞춰 UI를 분리함으로써, 각 위젯은 자신의 책임에만 집중할 수 있었고, 이는 협력 플레이 경험의 기반이 되는 명확하고 직관적인 UI 시스템으로 이어졌습니다.
