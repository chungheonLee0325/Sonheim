# 2.2. 컴포넌트 기반 설계 (Component-Based Design)

## 2.2.1. 설계 철학: "상속보다 조립(Composition over Inheritance)"

Sonheim 프로젝트는 "갓 클래스(God Class)"를 방지하고 장기적인 유지보수성과 확장성을 확보하기 위해 **컴포넌트 기반 설계**를 아키텍처의 핵심 원칙으로 삼습니다. 이는 거대한 단일 클래스가 모든 기능을 상속받아 구현하는 대신, 각 핵심 기능을 독립적인 `UActorComponent`로 분리하고, 액터는 이 컴포넌트들을 부품처럼 '조립'하여 완성하는 설계 방식입니다.

이러한 설계는 다음과 같은 명확한 목표를 달성하기 위해 채택되었습니다.

1.  **명확한 책임 분리 (Separation of Concerns):** 각 컴포넌트는 체력 관리, 상호작용, 인벤토리 등 단 하나의 명확한 책임만 갖습니다.
2.  **모듈성 및 재사용성:** 잘 만들어진 컴포넌트는 플레이어, 몬스터, 심지어는 파괴 가능한 오브젝트에도 쉽게 부착하여 기능을 재사용할 수 있습니다.
3.  **유연한 확장성:** 새로운 기능을 추가할 때, 기존 코드를 수정하는 대신 새로운 컴포넌트를 만들어 부착하기만 하면 되므로, 시스템을 안전하게 확장할 수 있습니다.

## 2.2.2. 핵심 구현: 조립, 퍼사드, 그리고 통신

#### 1단계: 기능의 "조립" (Composition)

Sonheim의 컴포넌트 아키텍처는 공통 기반 클래스인 `AAreaObject`를 중심으로 구성됩니다. `AAreaObject`는 모든 '살아있는 개체'가 공통으로 가져야 할 핵심 기능 컴포넌트들을 멤버 변수로 선언하여 '소유'하는 뼈대 역할을 합니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/AreaObject/Base/AreaObject.h#L133)
```cpp
// Source/Sonheim/AreaObject/Base/AreaObject.h
UCLASS()
class SONHEIM_API AAreaObject : public ACharacter
{
    // ...
public:
	// === Attribute ===
	UPROPERTY(BlueprintReadWrite)
	UHealthComponent* m_HealthComponent;
	UPROPERTY(BlueprintReadWrite)
	UConditionComponent* m_ConditionComponent;
	UPROPERTY(BlueprintReadWrite)
	class UStaminaComponent* m_StaminaComponent;
    // ...
	// === Skill System ===
	UPROPERTY(VisibleAnywhere, BlueprintReadOnly, Category = "Skill")
	class USonheimSkillComponent* m_SkillComponent;
};
```

`ASonheimPlayer`와 같은 자식 클래스는 `AAreaObject`로부터 공통 컴포넌트를 물려받는 동시에, 자신에게만 필요한 특화된 컴포넌트들을 추가로 "조립"하여 기능을 확장합니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/AreaObject/Player/SonheimPlayer.h#L458)
```cpp
// Source/Sonheim/AreaObject/Player/SonheimPlayer.h
UCLASS()
class SONHEIM_API ASonheimPlayer : public AAreaObject
{
    // ...
private:
	// 상호작용 컴포넌트
	UPROPERTY(VisibleAnywhere, BlueprintReadOnly, Category = "Interaction", meta = (AllowPrivateAccess = "true"))
	class UInteractionComponent* InteractionComponent;

	// ...
	UPROPERTY()
	class UPalPartnerSkillComponent* PalPartnerSkillComponent;
	UPROPERTY()
	class UPalCaptureComponent* PalCaptureComponent;
};
```

#### 2단계: 퍼사드 패턴(Facade Pattern)을 통한 API 제공

`AAreaObject`는 외부 시스템이 `HealthComponent`의 존재나 내부 구현을 알 필요 없이, 자신을 통해 안전하게 기능에 접근할 수 있도록 간단하고 통일된 API를 제공합니다. 이는 시스템 간의 결합도를 낮추는 **퍼사드 패턴**의 예시입니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/AreaObject/Base/AreaObject.h#L62)
```cpp
// Source/Sonheim/AreaObject/Base/AreaObject.h
// Health 기능 퍼사드 제공
UFUNCTION(BlueprintCallable, Category = "HP")
virtual float DecreaseHP(float Delta);
```

외부에서는 `Player->DecreaseHP()`와 같이 간단하게 함수를 호출할 뿐이며, 실제 체력 변경 로직은 `AAreaObject`가 내부적으로 `HealthComponent`에 위임하여 처리합니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/AreaObject/Base/AreaObject.cpp#L703)
```cpp
// Source/Sonheim/AreaObject/Base/AreaObject.cpp
float AAreaObject::DecreaseHP(float Delta)
{
	m_HealthComponent->ModifyHP(-Delta);
	return m_HealthComponent->GetHP();
}
```

*   **장점:** 외부 클래스는 `AAreaObject`에 어떤 컴포넌트가 있는지 알 필요 없이, `Player->DecreaseHP()`와 같이 간단하게 함수를 호출할 수 있습니다. 이는 외부 클래스와 내부 컴포넌트 간의 결합도를 낮춥니다.
*   **Trade-Off:** 반면, `AAreaObject`와 `UHealthComponent` 사이의 결합도는 약간 증가합니다. 만약 `UHealthComponent`의 `ModifyHP` 함수 시그니처가 변경되면, `AAreaObject`의 `DecreaseHP` 함수도 함께 수정되어야 합니다. 이 설계는 약간의 내부적 결합도를 감수하는 대신, 외부 시스템 전체의 편의성과 독립성을 크게 향상시키는 합리적인 선택입니다.


#### 3단계: 델리게이트를 이용한 컴포넌트 간 통신

컴포넌트들이 서로의 상태 변화를 알아야 할 때, 직접 참조하는 대신 **델리게이트(Delegate)**를 사용합니다. `InventoryComponent`는 장비가 변경되었을 때 `OnEquipmentChanged` 델리게이트를 호출하여 "장비가 변경되었다"는 사실만 외부에 알립니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/AreaObject/Player/Utility/InventoryComponent.h#L21)
```cpp
// Source/Sonheim/AreaObject/Player/Utility/InventoryComponent.h
DECLARE_DYNAMIC_MULTICAST_DELEGATE_TwoParams(FOnEquipmentChanged, EEquipmentSlotType, Slot, FInventoryItem, InventoryItem);

// ...

UPROPERTY(BlueprintAssignable, Category="Events")
FOnEquipmentChanged OnEquipmentChanged;
```

이 신호를 받은 `PlayerController`는, 자신이 관리하는 `InventoryWidget`의 UI를 갱신하도록 연결해주는 '중재자' 역할을 수행합니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/AreaObject/Player/SonheimPlayerController.cpp#L581)
```cpp
// Source/Sonheim/AreaObject/Player/SonheimPlayerController.cpp
// 메뉴가 열릴 때, InventoryComponent의 이벤트에 InventoryWidget의 함수를 바인딩
m_PlayerState->m_InventoryComponent->OnEquipmentChanged.AddDynamic(InventoryWidget, &UInventoryWidget::UpdateEquipmentFromData);
```

이러한 중재자 패턴을 통해, `InventoryComponent`는 UI의 존재를 알 필요가 없고, UI는 `InventoryComponent`의 내부 로직을 알 필요 없이, 서로 완벽하게 분리된 채 각자의 역할에만 집중할 수 있습니다.

## 2.2.3. 설계의 이점

*   **높은 유연성:** 기능이 독립적인 부품(컴포넌트)으로 존재하기 때문에, 필요한 기능을 자유롭게 "조립"하여 원하는 액터를 만들 수 있습니다.
*   **낮은 결합도:** 퍼사드 패턴과 델리게이트 통신을 통해, 각 컴포넌트와 시스템은 서로의 내부 구현을 알 필요 없이 약속된 인터페이스와 이벤트를 통해서만 상호작용합니다.
*   **명확한 책임:** `AAreaObject`는 컴포넌트를 소유하고 외부 API를 제공하며, `PlayerController`는 컴포넌트 간의 통신을 중재하고, 각 컴포넌트는 자신의 고유 로직에만 집중하는 등 역할 분담이 명확합니다.
