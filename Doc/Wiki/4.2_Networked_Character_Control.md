# 4.2. 네트워크 캐릭터 컨트롤 (Networked Character Control)

## 4.2.1. 설계 목표

플레이어의 부드럽고 반응성 좋은 움직임은 게임의 몰입감에 매우 중요합니다. 멀티플레이 환경에서는 모든 플레이어에게 각 캐릭터의 움직임이 동일하게 보여야 하므로, 다음 목표를 가지고 네트워크 컨트롤 시스템을 설계했습니다.

1.  **서버 권위의 이동 판정:** 플레이어의 이동은 반드시 서버의 검증을 거쳐야 합니다. 이는 속도 핵, 비정상적인 점프 등의 치트를 원천적으로 방지하고 공정성을 보장합니다.
2.  **즉각적인 클라이언트 반응성:** 서버의 응답을 기다린 후에야 캐릭터가 움직인다면 플레이어는 극심한 지연(Lag)을 느낍니다. 이를 해결하기 위해, 클라이언트는 입력을 받는 즉시 캐릭터를 스스로 움직이는 **클라이언트 예측(Client-Side Prediction)**을 사용합니다.
3.  **효율적인 동기화:** 캐릭터의 모든 움직임을 매 프레임 전송하는 대신, 언리얼 엔진의 `CharacterMovementComponent`가 제공하는 고도로 최적화된 동기화 메커니즘을 최대한 활용하여 네트워크 대역폭 사용을 최소화합니다.
4.  **상태 기반의 깊이 있는 조작:** 플레이어의 다양한 상태(달리기, 구르기, 글라이딩 등)에 따라 다른 행동이 제약되거나 가능하도록 설계하여 깊이 있는 조작감을 제공합니다.

---

## 4.2.2. 아키텍처: 두 가지 동기화 방식

Sonheim의 캐릭터 동기화는 두 가지 방식으로 이루어집니다.

1.  **표준 이동 동기화 (By Engine):** 걷기, 달리기, 점프, 낙하 등 기본적인 이동은 언리얼 엔진의 `UCharacterMovementComponent`가 내부적으로 클라이언트 예측, 서버 보정, 부드러운 보간 등 모든 복잡한 과정을 자동으로 처리합니다.
2.  **커스텀 액션/상태 동기화 (By Developer):** 구르기, 글라이딩, 공격 등 `CharacterMovementComponent`가 자동으로 처리해주지 않는 커스텀 행동들은 개발자가 직접 **RPC**와 **변수 복제(Variable Replication)**를 사용하여 수동으로 동기화 로직을 구현해야 합니다.

---

## 4.2.3. 핵심 구현 패턴

#### 1. 표준 이동: `AddMovementInput` 호출이 전부

개발자는 `PlayerController`에서 입력을 받아 `Pawn`의 `Move` 함수를 호출하고, `Pawn`은 이 입력을 받아 `AddMovementInput` 함수를 호출하기만 하면 됩니다. 클라이언트 예측과 서버 동기화는 엔진이 모두 처리해줍니다.

```cpp
// SonheimPlayer.cpp - 실제 Pawn의 이동 처리 함수
void ASonheimPlayer::Move(const FVector2D MovementVector)
{
    if (Controller != nullptr)
    {
        // ... 이동 방향 계산 ...
        // 상태 체크 후 실제 이동 입력 추가
        if (CanPerformAction(CurrentPlayerState, "Move"))
        {
            AddMovementInput(ForwardDirection, MovementVector.Y);
            AddMovementInput(RightDirection, MovementVector.X);
        }
    }
}
```

#### 2. 커스텀 액션 동기화 (스킬 시스템): "구르기"

한 번의 이벤트로 끝나는 액션은 `Client -> Server` RPC 패턴을 사용하되, 실제 로직은 **스킬 시스템**에 위임하여 일관성을 유지합니다.

1.  **[Client]** `PlayerController`가 입력을 받아 `ASonheimPlayer::Dodge_Pressed()`를 호출합니다.
2.  **[Client → Server]** `Dodge_Pressed` 함수는 즉시 `Server_Dodge_Pressed()` RPC를 호출하여 서버에 액션 수행을 요청합니다.
3.  **[Server]** `Server_Dodge_Pressed_Implementation` 함수는 회피 동작을 ID `2`번 스킬로 취급하고, `CastSkill` 함수를 호출하여 스킬 시전을 시도합니다.
4.  **[Server, Skill System]** `CastSkill` 내부에서 스태미나 조건, 쿨타임 등을 모두 검사하고, 성공 시 스킬을 활성화합니다. 스킬 데이터에 연결된 애니메이션 몽타주가 재생되고, 상태 이상(무적)이 적용되는 등 모든 관련 로직이 스킬 시스템을 통해 처리됩니다. 이 결과는 변수 복제를 통해 모든 클라이언트에 동기화됩니다.

#### 3. 커스텀 상태 동기화 (`ReplicatedUsing`): "글라이딩"

지속적인 상태는 변수 복제를 사용하는 것이 훨씬 효율적입니다.

1.  **[Client → Server]** 플레이어가 글라이더 활성화 키를 누르면, 서버에 `Server_SetGliding(true)` RPC를 요청합니다.
2.  **[Server]** 서버는 글라이딩 가능 상태인지 확인한 후, `CharacterMovementComponent`의 이동 모드를 `MOVE_Flying`으로 변경하고, `GravityScale`을 0에 가깝게 낮추는 등 물리 속성을 변경합니다. 이 변경된 물리 속성 값들은 `Replicated`로 지정되어 있어 클라이언트에 자동으로 동기화됩니다.
3.  **[Server]** 글라이딩 상태임을 나타내는 `bIsGliding` 변수(UPROPERTY `ReplicatedUsing=OnRep_IsGliding`)의 값을 `true`로 변경합니다.
4.  **[Client]** `bIsGliding` 값이 클라이언트에 복제되면, `OnRep_IsGliding` 함수가 자동으로 호출됩니다. 이 함수 안에서 글라이더 메쉬를 보이게 하거나, 관련 사운드를 재생하는 등 시각적/청각적 처리를 수행합니다.

## 4.2.4. 고급 구현 사례: 상태 기반 전투 로직

캐릭터 컨트롤은 다른 시스템과 유기적으로 연동됩니다. 예를 들어, 플레이어의 일반 공격(`LeftMouse_Pressed`)은 파트너 스킬의 사용 여부에 따라 완전히 다른 로직을 수행합니다.

```cpp
// SonheimPlayer.cpp
void ASonheimPlayer::Server_LeftMouse_Pressed_Implementation()
{
    // 파트너 스킬이 우선순위를 가짐
    if (PalPartnerSkillComponent && PalPartnerSkillComponent->IsUsingPartnerSkill())
    {
       // 일반 공격 대신 파트너 스킬의 특수 효과를 발동
       PalPartnerSkillComponent->SetPartnerSkillTrigger(true);
       return;
    }

    // 일반 공격 로직 수행...
}
```

또한, 스킬이 시전되면 플레이어의 상태를 `EPlayerState::ACTION`으로 변경하여 다른 행동(점프, 구르기 등)을 막고, 스킬이 끝났을 때 다시 `Normal` 상태로 돌아오도록 델리게이트(`OnSkillComplete`)를 바인딩하여 정교한 컨트롤을 구현합니다.

## 4.2.5. 구현 경험 및 트러블슈팅

### 구현 경험 및 교훈: 왜 멀티캐스트 대신 `ReplicatedUsing`을 써야 하는가?

*   **문제:** 개발 초기에는 '사망', '글라이더 활성화', '무기 장착' 같은 상태 변화의 시각적 처리를 `NetMulticast` RPC로 모든 클라이언트에 전파했습니다. 이 방식은 모든 플레이어가 세션에 함께 있을 때는 잘 동작하는 것처럼 보였습니다. 하지만 결정적으로, **중간에 참여하는 플레이어(Late-Joiner)에게는 이전에 발생한 멀티캐스트 RPC가 전달되지 않는 문제**가 있었습니다. 예를 들어, 어떤 플레이어가 이미 죽은 상태에서 다른 플레이어가 게임에 접속하면, 새로 접속한 플레이어의 화면에서는 그 캐릭터가 멀쩡히 살아있는 것으로 보이는 동기화 오류가 발생했습니다.

*   **해결:** 이 문제를 해결하기 위해 언리얼 엔진의 네트워크 원칙을 다시 학습했고, 상태 동기화의 패러다임을 `NetMulticast` RPC에서 **변수 복제와 `ReplicatedUsing`(RepNotify)을 사용하는 방식**으로 전면 수정했습니다.
    1.  상태를 나타내는 변수(예: `bIsGliding`, `bIsDead`)를 `UPROPERTY(ReplicatedUsing=...)`으로 선언합니다.
    2.  서버는 상태가 변경될 때 이 변수의 값만 변경합니다.
    3.  변수 값의 변경은 엔진에 의해 자동으로 모든 클라이언트(기존 및 신규)에게 복제됩니다.
    4.  값이 클라이언트에 도착하면, `ReplicatedUsing`에 지정된 `OnRep_...` 함수가 **자동으로 호출**됩니다.
    5.  모든 시각적/논리적 처리(애니메이션 재생, 메시 표시, UI 변경 등)는 이 `OnRep_...` 함수 안에서 수행합니다.

    ```cpp
    // SonheimPlayer.h
    // 글라이딩 상태를 나타내는 변수. ReplicatedUsing으로 OnRep_IsGliding 함수와 연결됩니다.
    UPROPERTY(ReplicatedUsing=OnRep_IsGliding)
    bool bIsGliding = false;

    // bIsGliding 값이 변경될 때 모든 클라이언트에서 호출될 함수
    UFUNCTION()
    void OnRep_IsGliding();

    // SonheimPlayer.cpp
    // 서버에서 글라이딩 상태를 변경하는 함수
    void ASonheimPlayer::Server_SetGliding_Implementation(bool bNew)
    {
        // ... 각종 조건 검사 ...
        bIsGliding = bNew; // 1. 서버에서 변수 값 변경
        
        // 2. 서버 자신에게도 RepNotify를 즉시 적용하기 위해 수동 호출
        ApplyGliderState(bIsGliding); 
    }

    // 3. 클라이언트에서는 RepNotify에 의해 이 함수가 자동으로 호출됨
    void ASonheimPlayer::OnRep_IsGliding()
    {
        // 4. 실제 시각적/기능적 처리는 여기서 수행
        ApplyGliderState(bIsGliding);
    }
    ```

*   **교훈:** **일회성 이벤트가 아닌, 지속되어야 하는 '상태(State)'를 동기화할 때는 반드시 `NetMulticast`가 아닌 변수 복제(`Replication`)를 사용해야 한다**는 핵심 원칙을 깨달았습니다. `NetMulticast`는 모든 클라이언트에게 '지금 당장 이 함수를 실행해!'라고 외치는 일회성 명령에 가깝지만, 변수 복제는 '이 캐릭터의 상태는 이것이다'라는 사실 자체를 보장해줍니다. 이 방식은 중간 참여자를 포함한 모든 클라이언트에게 항상 정확한 상태를 보장하는 가장 견고하고 안정적인 방법입니다.


#### 리팩토링: God Class에서 이벤트 기반 컴포넌트로

*   **과정:** 프로젝트 초기에는 모든 기능을 `ASonheimPlayer`에 구현하여 'God Class'가 되는 문제가 있었습니다. 이를 해결하기 위해 1차적으로 각 기능을 독립적인 컴포넌트로 분리했고, 2차적으로는 컴포넌트 간의 직접 참조로 인한 스파게티 코드를 해결하기 위해 델리게이트를 활용한 이벤트 기반 설계로 개선했습니다.
*   **교훈:** 이 과정을 통해, 단순히 기능을 구현하는 것을 넘어 유지보수와 확장이 용이한 견고한 아키텍처를 구축하는 경험을 할 수 있었습니다.
