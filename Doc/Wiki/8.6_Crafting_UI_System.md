# 8.6. 제작 UI 시스템: 역할 기반의 다층적 UI와 성능 최적화

## 8.6.1. 설계 목표

제작 기능은 단순히 하나의 UI 창으로 이루어지지 않습니다. 플레이어의 상황과 역할에 따라 각기 다른 정보를 제공하는 여러 UI 위젯들의 유기적인 협력으로 완성됩니다. 이 시스템은 다음과 같은 목표를 가지고 설계되었습니다.

1.  **명확한 역할 분담:** 각 위젯은 단 하나의 명확한 책임을 가집니다. 상호작용을 유도하는 위젯, 레시피를 선택하는 위젯, 진행 상황을 공유하는 위젯으로 역할을 분리하여 코드의 복잡성을 낮추고 유지보수성을 높입니다.
2.  **컨텍스트 기반 정보 제공:** 플레이어가 제작대를 처음 봤을 때, 제작을 진행 중일 때, 제작이 완료되었을 때 등 각기 다른 상황에 맞는 UI를 제공하여 직관적인 사용자 경험을 만듭니다.
3.  **공개 정보와 개인 정보의 분리:** 모든 플레이어에게 보여줘야 할 정보(제작 진행률)와, 오직 제작을 시작한 플레이어에게만 보여줘야 할 정보(레시피 목록)를 처리하는 UI를 명확하게 분리합니다.
4.  **효율적인 UI 갱신 및 성능 최적화:** 레시피를 선택할 때마다 모든 UI 요소를 파괴하고 새로 그리는 대신, 변경이 필요한 부분만 선택적으로 갱신하고 **오브젝트 풀링(Object Pooling)**을 적용하여 성능 부하를 최소화합니다.

---

## 8.6.2. 아키텍처: 세 위젯의 협력

제작 기능은 `DetectWidget`, `CraftingWidget`, `CraftingQueueWidget`이라는 세 가지 핵심 위젯이 `ACraftingStation`이라는 단일 데이터 소스를 중심으로 협력하는 구조입니다.

*   **`DetectWidget` (초대장):** 플레이어가 제작대를 바라볼 때, `ACraftingStation`의 상태에 따라 "레시피 선택", "작업 돕기" 등 컨텍스트에 맞는 텍스트를 표시하여 상호작용을 유도합니다.
*   **`CraftingWidget` (개인 제어판):** 제작을 시작한 플레이어 **한 명에게만** 보이는 개인 UI입니다. 제작 가능한 레시피 목록을 보여주고, 재료를 확인하며, 실제 제작을 시작하도록 서버에 요청하는 핵심적인 역할을 합니다.
*   **`CraftingQueueWidget` (공개 정보 게시판):** 제작대 주변의 **모든 플레이어**에게 보이는 공유 UI입니다. 현재 제작 중인 아이템, 남은 시간 등 공개적인 진행 상황을 실시간으로 표시합니다.

## 8.6.3. 코드 심층 분석: `CraftingWidget`의 효율적인 UI 재구성

`UCraftingWidget`은 제작 UI의 핵심으로, 효율적인 UI 갱신을 위한 여러 최적화 기법이 적용되어 있습니다.

#### 1. 레시피 목록 구성 (`RefreshRecipes`)

위젯이 처음 열릴 때, `RefreshRecipes` 함수는 `ACraftingStation`에 연결된 데이터 테이블을 읽어, 제작 가능한 모든 레시피에 대한 `SlotWidget`을 생성하여 좌측 패널(`RecipeWrap`)에 채웁니다. 이 때, 각 레시피의 제작 가능 여부(`bCraftable`)를 미리 계산하여, 재료가 부족한 레시피는 반투명하고 붉은 틴트를 적용하는 시각적 피드백을 제공합니다.

#### 2. 정적/동적 데이터 분리를 통한 선택적 갱신 (`RefreshDetail`)

플레이어가 레시피를 선택할 때마다 우측의 상세 정보 패널이 갱신됩니다. 이 때 모든 정보를 무조건 새로 그리는 대신, `RefreshDetail` 함수는 정적 정보와 동적 정보를 구분하여 처리합니다.

*   **`RebuildStaticForRecipe` (정적 정보 갱신):** 이 함수는 **선택된 레시피 자체가 변경되었을 때만 호출**됩니다. 결과 아이템의 이름, 아이콘, 그리고 **재료 목록의 레이아웃**처럼 한 번 설정되면 바뀌지 않는 요소들을 구성합니다.
*   **`RefreshDynamicForRecipe` (동적 정보 갱신):** 이 함수는 레시피가 선택될 때 뿐만 아니라, **제작 수량을 조절하거나 플레이어의 인벤토리가 변경될 때마다 항상 호출**됩니다. 재료의 필요 수량/보유 수량 텍스트, 텍스트 색상(재료 부족 시 빨간색), 제작 버튼의 활성화 여부 등 실시간으로 변해야 하는 정보들만 선택적으로 갱신합니다.

이러한 분리 덕분에, 플레이어가 제작 수량만 조절할 때는 비용이 비싼 재료 목록 위젯들을 새로 그리거나 레이아웃을 재계산할 필요 없이, 오직 텍스트만 갱신하여 높은 성능을 유지합니다.

#### 3. 위젯 오브젝트 풀링 (`RebuildStaticForRecipe`)

`RebuildStaticForRecipe` 함수의 가장 핵심적인 최적화는 **재료 목록 위젯에 대한 오브젝트 풀링**입니다. 필요한 재료 위젯의 개수와 현재 풀에 보관된 위젯의 개수를 비교하여, 부족하면 새로 생성하고 남으면 파괴하는 대신 `Collapsed`로 숨겨 재활용합니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/UI/Widget/GameObject/Crafting/CraftingWidget.cpp#L195)
```cpp
// Source/Sonheim/UI/Widget/GameObject/Crafting/CraftingWidget.cpp
void UCraftingWidget::RebuildStaticForRecipe(const struct FCraftingRecipe* R)
{
    // ...
    // 풀이 필요한 위젯 수보다 작으면, 부족한 만큼 새로 생성하여 풀에 추가
    while (RequiredRowPool.Num() < CachedMatIDs.Num())
    {
        URequiredMatRowWidget* RowW = CreateWidget<URequiredMatRowWidget>(...);
        RequiredRowPool.Add(RowW);
        RequiredList->AddChild(RowW);
    }

    // 풀에 있는 모든 위젯을 순회하며 가시성 조절
    for (int32 i = 0; i < RequiredRowPool.Num(); ++i)
    {
        const bool bVisible = (i < CachedMatIDs.Num());
        RequiredRowPool[i]->SetVisibility(bVisible ? ESlateVisibility::Visible : ESlateVisibility::Collapsed);
        // ...
    }
}
```
이 오브젝트 풀링 기법을 통해, 재료가 많은 레시피와 적은 레시피 사이를 반복적으로 오가더라도 위젯의 생성(`CreateWidget`)과 소멸(Garbage Collection)에 따른 성능 부하를 원천적으로 방지하여, 부드러운 UI 경험을 제공합니다.

## 8.6.4. 구현 경험: 이벤트 기반 실시간 데이터 연동

#### 문제 정의: 외부 요인으로 인한 데이터 변경에 어떻게 반응할 것인가?

제작 UI의 핵심 기능 중 하나는 플레이어의 현재 재료 보유량을 실시간으로 반영하는 것입니다. 만약 플레이어가 제작 UI를 열어둔 상태에서 월드의 다른 아이템을 주워 재료의 개수가 변경되었다면, UI는 이 변경을 즉시 감지하고 '보유 수량' 텍스트와 '제작 가능' 여부를 다시 계산해야 합니다.

가장 단순한 방법은 매 프레임(`Tick`)마다 인벤토리를 확인하는 것이지만, 이는 불필요한 성능 낭비를 유발하는 최악의 방식입니다. 그렇다면 UI는 어떻게 데이터의 변경을 '알 수' 있을까요?

#### 해결 방안: `OnInventoryChanged` 델리게이트 구독

이 문제를 해결하기 위해, [8.1. UI 아키텍처 및 이벤트 시스템](./8.1_UI_Architecture_and_Event_System.md)에서 정의한 프로젝트의 핵심 아키텍처, 즉 **이벤트 기반 데이터 연동**을 일관되게 사용합니다. `CraftingWidget`은 데이터 소스인 `InventoryComponent`를 직접 감시하는 대신, `InventoryComponent`가 스스로 "내용이 변경되었다"고 방송하는 `OnInventoryChanged` 이벤트를 구독합니다.

1.  **이벤트 구독 (Subscribe):** `CraftingWidget`이 초기화될 때, 플레이어의 `InventoryComponent`에 접근하여 `OnInventoryChanged` 델리게이트에 자신의 `UpdateInventoryFromData` 함수를 등록합니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/UI/Widget/GameObject/Crafting/CraftingWidget.cpp#L19)
```cpp
// Source/Sonheim/UI/Widget/GameObject/Crafting/CraftingWidget.cpp
void UCraftingWidget::Initialise(ACraftingStation* InStation)
{
    // ... InventoryComp 참조 획득 ...

    if (InventoryComp)
    {
        InventoryComp->OnInventoryChanged.AddDynamic(this, &UCraftingWidget::UpdateInventoryFromData);
    }
}
```

2.  **이벤트 처리 (Handle):** 이제 `InventoryComponent`의 내용이 변경되어 `OnInventoryChanged` 이벤트가 발생하면, `CraftingWidget`의 `UpdateInventoryFromData` 함수가 자동으로 호출됩니다. 이 함수는 UI 전체를 새로 그리는 대신, 이미 최적화된 `RefreshDetail` 함수를 호출하여 변경이 필요한 부분만 효율적으로 갱신합니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/UI/Widget/GameObject/Crafting/CraftingWidget.cpp#L311)
```cpp
// Source/Sonheim/UI/Widget/GameObject/Crafting/CraftingWidget.cpp
void UCraftingWidget::UpdateInventoryFromData(const TArray<FInventoryItem>& InventoryData)
{
    RefreshDetail();
}
```

3.  **구독 해제 (Unsubscribe):** 위젯이 파괴될 때(`NativeDestruct`), 델리게이트 구독을 해제하여 메모리 누수나 충돌을 방지합니다. 이는 안정적인 시스템을 위한 필수적인 과정입니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/UI/Widget/GameObject/Crafting/CraftingWidget.cpp#L66)
```cpp
// Source/Sonheim/UI/Widget/GameObject/Crafting/CraftingWidget.cpp
void UCraftingWidget::NativeDestruct()
{
    if (InventoryComp)
    {
        InventoryComp->OnInventoryChanged.RemoveDynamic(this, &UCraftingWidget::UpdateInventoryFromData);
    }
    Super::NativeDestruct();
}
```

#### 설계의 이점: 아키텍처의 일관성과 효율성

이 설계를 통해, `CraftingWidget`은 "언제 인벤토리가 변하는가"를 전혀 신경 쓸 필요 없이, 오직 "인벤토리가 변했다고 통보받으면 무엇을 할 것인가"에만 집중할 수 있습니다. 이는 `CraftingWidget`과 `InventoryComponent` 사이의 결합도를 낮추고, 프로젝트 전체에 걸쳐 일관된 이벤트 기반 아키텍처를 유지하게 해줍니다. 또한, 이 이벤트는 '오브젝트 풀링'과 '선택적 갱신' 로직을 작동시키는 효율적인 '방아쇠' 역할을 하여, 시스템의 반응성과 성능을 모두 보장합니다.
