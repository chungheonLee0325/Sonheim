# 7.3. UI 최적화: 오브젝트 풀링

> ### UI 사용 패턴에 따른 최적화: 전역 액터 풀링과 지역 위젯 풀링
> 
> *   **두 가지 문제:** UI 요소는 사용 패턴에 따라 다른 최적화 문제를 야기합니다. 데미지 숫자처럼 **예측 불가능한 시점에 월드 어디서든** 필요한 UI가 있고, 제작 재료 목록처럼 **특정 UI 내부에서만 반복적으로** 사용되는 UI가 있습니다.
> *   **두 가지 해법:** 이 두 가지 다른 문제에 맞춰 각기 다른 최적화 해법을 적용했습니다. 전자는 **전역 액터 풀(Global Actor Pool)**로, 후자는 **지역 위젯의 가시성 제어(Local Widget Visibility Control)** 방식으로 해결하여 성능과 유지보수성을 모두 잡았습니다.
> *   **성과:** 이 상황에 맞는 최적화 전략을 통해, 수십 개의 데미지 숫자가 동시에 표시되는 난전 상황과 수십 개의 재료가 필요한 복잡한 UI를 여는 상황 모두에서 프레임 드랍 없는 안정적인 성능을 확보했습니다.

## 7.3.1. 구현 기능 목록 (Feature List)

이 최적화 전략을 통해 플레이어가 실제로 체감할 수 있는 성능 향상 및 기능은 다음과 같습니다.

*   **끊김 없는 전투 경험:** 수십 개의 데미지 숫자가 화면을 뒤덮는 대규모 전투 상황에서도 프레임 저하 없이 부드러운 게임 플레이가 가능합니다.
*   **즉각적인 UI 반응:** 재료가 50개가 넘는 복잡한 제작 레시피를 선택해도, UI의 지연이나 끊김 현상 없이 재료 목록이 즉시 표시됩니다.
*   **풍부한 시각적 피드백:** 약점 공격, 속성 상성에 따른 데미지 변화가 각기 다른 색상, 크기, 외곽선으로 표현되어, 플레이어는 자신의 공격이 얼마나 효과적인지 즉시 인지할 수 있습니다.
*   **시각적 피드백 보장:** 예측 불가능한 수준의 이펙트가 발생해도 데미지 숫자는 절대 유실되지 않습니다. 시스템은 가장 오래된 액터를 재활용하여 항상 시각적 피드백을 보장합니다.

---

## 7.3.2. 기술 상세 (Technical Deep Dive)

### 7.3.2.1. 아키텍처: 두 가지 풀링 전략

풀링(Pooling)은 자주 사용되는 객체를 미리 생성하여 비활성 상태로 '풀(Pool)'에 보관하고, 필요할 때 가져와 활성화한 뒤, 사용이 끝나면 파괴하는 대신 다시 풀에 반납하여 재사용하는 기법입니다. Sonheim에서는 두 가지 주요 영역에 이 기법이 적용되었습니다.

1.  **전역 액터 풀링 (Global Actor Pooling):** 데미지 숫자처럼 **전역적이고 예측 불가능하게** 사용되는 UI는, 월드에 단 하나만 존재하는 싱글톤 매니저(`AFloatingDamagePool`)가 `AActor` 기반 위젯을 재활용하여 관리합니다.
2.  **지역 위젯 풀링 (Local Widget Pooling):** 제작 재료 목록처럼 **지역적이고 구조적으로** 사용되는 UI는, 부모 위젯(`UCraftingWidget`)이 자식 위젯들의 가시성(Visibility)만 제어하여 재사용합니다.

### 7.3.2.2. 핵심 구현 1: 전역 액터 풀링 (AFloatingDamagePool)

#### 7.3.2.2.1. 문제 정의 (The Problem)

왜 데미지 숫자는 특별한 시스템이 필요한가? 전투 중 수없이 생성과 소멸을 반복하며, 약점/속성에 따른 풍부한 시각적 정보까지 전달해야 하므로, 극심한 성능 저하를 유발할 수 있습니다. 이 두 가지 문제를 해결하기 위해 풀링 기반의 전용 시스템을 구축했습니다.

#### 7.3.2.2.2. 풀링 아키텍처 (The Pooling Architecture)

**1. 호출 (Call): `AAreaObject::TakeDamage`**

모든 데미지 숫자 표시의 시작점은 `AAreaObject`의 `TakeDamage` 함수입니다. 서버는 이 함수 안에서 약점, 속성 등을 모두 계산한 후, `MulticastDamageEffect` RPC를 호출하여 모든 클라이언트에게 데미지 정보를 전달합니다.

**2. 요청 (Request): `FDamageNumberRequest`**

클라이언트에서 호출된 `MulticastDamageEffect`는 `AFloatingDamagePool`의 `RequestDamageNumber` 함수를 호출합니다. 이 때, 데미지 정보를 담은 `FDamageNumberRequest` 구조체를 함께 전달하여, 풀링 시스템의 복잡성을 캡슐화하고 API를 단순하게 유지합니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/UI/FloatingDamagePool.h#L11)
```cpp
// Source/Sonheim/UI/FloatingDamagePool.h
USTRUCT(BlueprintType)
struct FDamageNumberRequest
{
    GENERATED_BODY()

    float Damage = 0.0f;
    FVector WorldLocation;
    TWeakObjectPtr<AActor> DamageCauser;
    TWeakObjectPtr<AActor> DamagedActor;
    EFloatingOutLineDamageType WeakPointType = EFloatingOutLineDamageType::Normal;
    EFloatingTextDamageType ElementAttributeType = EFloatingTextDamageType::Normal;
};

// ...

// Source/Sonheim/AreaObject/Base/AreaObject.cpp
void AAreaObject::MulticastDamageEffect_Implementation(...)
{
	if (AFloatingDamagePool* DamagePool = AFloatingDamagePool::GetInstance(GetWorld()))
	{
		FDamageNumberRequest Request;
		Request.Damage = Damage;
		Request.WorldLocation = HitLocation;
		Request.WeakPointType = bWeakPoint ? EFloatingOutLineDamageType::WeakPointDamage : EFloatingOutLineDamageType::Normal;
        // ... (속성 타입 설정)
		DamagePool->RequestDamageNumber(Request);
	}
}
```

**3. 활성화 (Activate): 동적 확장 및 재활용**

`GetPooledActor` 함수는 풀에 쉬고 있는 액터가 있으면 즉시 반환합니다. 만약 풀이 비어있다면, `MaxPoolSize`에 도달하기 전까지는 새 액터를 생성하여 대응하고, 최대치마저 도달했다면 현재 활성화된 액터 중 **가장 오래된 것을 강제로 재활용**하여 어떤 상황에서도 데미지 표시가 누락되지 않도록 보장합니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/UI/FloatingDamagePool.cpp#L85)
```cpp
// Source/Sonheim/UI/FloatingDamagePool.cpp
AFloatingDamageActor* AFloatingDamagePool::GetPooledActor()
{
	// 1. 사용 가능한 액터가 있으면 즉시 반환
	if (Pool.Num() > 0)
	{
		return Pool.Pop();
	}

	// 2. 풀이 비었고 최대치 미만이면 새로 생성
	if (ActiveActors.Num() < MaxPoolSize)
	{
		return GetWorld()->SpawnActor<AFloatingDamageActor>(...);
	}

	// 3. 최대치에 도달했다면, 가장 오래된 액터를 강제 재활용
	if (ActiveActors.Num() > 0)
	{
		return ActiveActors[0];
	}

	return nullptr;
}
```

**4. 자동 반납 (Self-Return): "Fire and Forget"**

`AFloatingDamageActor`는 자신의 수명(`LifeTime`)이 다하면, `Tick` 함수에서 스스로 `ReturnToPool()`을 호출하여 풀에 복귀합니다. 이 "자동 반납" 설계 덕분에, 데미지 표시를 요청한 객체는 자신이 사용한 액터를 추적하거나 관리할 책임이 전혀 없는 **"Fire and Forget"** 방식의 편리한 사용이 가능합니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/UI/FloatingDamageActor.cpp#L118)
```cpp
// Source/Sonheim/UI/FloatingDamageActor.cpp
void AFloatingDamageActor::Tick(float DeltaTime)
{
	Super::Tick(DeltaTime);
	// ... (애니메이션 로직)

	CurrentLifeTime += DeltaTime;
	if (CurrentLifeTime >= LifeTime)
	{
		ReturnToPool(); // 수명이 다하면 스스로 풀에 복귀
	}
}
```

#### 7.3.2.2.3. 풀링된 오브젝트의 기능 (The Pooled Object's Feature)

풀링을 통해 효율적으로 관리되는 `AFloatingDamageActor`는, `UFloatingDamageWidget`을 통해 다음과 같이 풍부한 시각적 피드백을 표시하는 기능을 담당합니다. `SetDamageInfo` 함수는 `FDamageNumberRequest`의 열거형 값을 받아, 데미지 종류에 따라 UI의 색상, 외곽선 등을 다르게 설정합니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/UI/Widget/FloatingDamageWidget.cpp#L29)
```cpp
// Source/Sonheim/UI/Widget/FloatingDamageWidget.cpp
void UFloatingDamageWidget::SetDamageInfo(float Damage, EFloatingOutLineDamageType WeakPointType, EFloatingTextDamageType ElementAttributeType)
{
    // ...
    // 텍스트 색상 설정 (속성에 따라)
    if (const FLinearColor* Color = DamageElementAttributeColors.Find(ElementAttributeType))
    {
        DamageText->SetColorAndOpacity(FSlateColor(*Color));
    }

    // 외곽선 색상 설정 (약점 여부에 따라)
    FSlateFontInfo FontInfo = DamageText->GetFont();
    if (const FLinearColor* OutlineColor = DamageWeakPointColors.Find(WeakPointType))
    {
        FontInfo.OutlineSettings.OutlineColor = *OutlineColor;
    }
    DamageText->SetFont(FontInfo);
}
```

### 7.3.2.3. 핵심 구현 2: 지역 위젯 풀링 (UCraftingWidget)

제작 UI에서 다른 레시피를 선택하면, 필요한 재료의 종류와 개수가 모두 바뀝니다. 이 재료 목록을 표시하는 `URequiredMatRowWidget`들을 매번 파괴(`RemoveFromParent`)하고 생성(`CreateWidget`)하는 것은, 특히 재료가 많은 레시피의 경우 심각한 프레임 드랍을 유발합니다. 이러한 **지역적이고 반복적인** 사용 패턴에는 더 가볍고 간단한 최적화 방식이 필요했습니다.

**가시성 제어 (Visibility Control): 생성 대신 숨기기**

`UCraftingWidget`은 재료 목록 위젯들을 `RequiredRowPool`이라는 배열에 담아 직접 소유합니다. 레시피가 변경되면, `RebuildStaticForRecipe` 함수는 위젯을 파괴하는 대신, 필요한 만큼은 화면에 `Visible`로 만들고, 필요 없어진 나머지는 `Collapsed`로 설정하여 **단순히 숨깁니다.** `CreateWidget`은 풀의 크기가 부족할 때만 최소한으로 호출됩니다. 이는 `UObject`를 생성하고 가비지 컬렉션의 대상이 되게 하는 비싼 비용을, 훨씬 저렴한 `SetVisibility` 함수 호출로 대체하는 효과적인 최적화입니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/UI/Widget/GameObject/Crafting/CraftingWidget.cpp#L195)
```cpp
// Source/Sonheim/UI/Widget/GameObject/Crafting/CraftingWidget.cpp
void UCraftingWidget::RebuildStaticForRecipe(const FCraftingRecipe* R)
{
    // ...

    // 1. 풀이 필요한 위젯 수보다 작으면, 부족한 만큼만 새로 생성
    while (RequiredRowPool.Num() < CachedMatIDs.Num())
    {
        URequiredMatRowWidget* RowW = CreateWidget<URequiredMatRowWidget>(...);
        RequiredRowPool.Add(RowW);
        RequiredList->AddChild(RowW);
    }

    // 2. 풀에 있는 모든 위젯을 순회하며 가시성 제어
    for (int32 i = 0; i < RequiredRowPool.Num(); ++i)
    {
        const bool bVisible = (i < CachedMatIDs.Num());
        // 필요한 만큼은 보이게, 나머지는 숨겨서 재사용 대기
        RequiredRowPool[i]->SetVisibility(bVisible ? ESlateVisibility::Visible : ESlateVisibility::Collapsed);

        if (bVisible) RequiredRowPool[i]->UpdateRow(...); // 보이는 위젯은 데이터만 갱신
    }
}
```

### 7.3.2.4. 회고 및 개선점

*   **교훈: 상황에 맞는 최적화의 중요성**
    초기에는 모든 UI 요소에 적용할 수 있는 범용 풀링 시스템을 구상했습니다. 하지만 개발 과정에서 UI 요소의 사용 패턴이 크게 두 가지로 나뉜다는 것을 깨달았습니다. 데미지 숫자처럼 **전역적이고 예측 불가능하게** 사용되는 경우와, 제작 재료 목록처럼 **지역적이고 구조적으로** 사용되는 경우입니다. "하나의 풀링 전략이 모든 상황에 맞는 것은 아니다"라는 교훈을 얻었고, 각 문제에 맞는 최적의 도구(전역 액터 풀 vs 지역 위젯 가시성 제어)를 선택하는 것이 훨씬 효율적이고 직관적인 설계임을 배웠습니다.

*   **개선 제안: `UWorldSubsystem`으로 리팩토링**
    현재 `AFloatingDamagePool`은 `AActor` 기반의 싱글톤으로 구현되어 있습니다. 이 전역 관리자는 월드에 위치할 필요가 없고, 월드의 생명주기와 함께하며, 월드마다 하나씩만 존재하면 되는 "월드 단위 전역 서비스"의 특성을 완벽하게 만족하므로, 언리얼 엔진의 `UWorldSubsystem`으로 개선하는 것이 가장 이상적입니다.

    *   **장점 (Advantages):**
        1.  **라이프사이클 정합성:** 엔진이 레벨 로드/언로드, 심리스 트래블 시 서브시스템을 자동으로 생성/소멸시켜주므로, 싱글톤 액터를 직접 스폰하고 정적 포인터를 관리하는 현재 방식보다 훨씬 안전하고 코드가 간결해집니다.
        2.  **월드 다중성 대응:** PIE 다중 월드 환경이나 리슨 서버(호스트/원격 클라이언트) 구도에서, 각 월드마다 정확히 하나의 인스턴스가 존재함을 엔진 레벨에서 보장해줍니다.
        3.  **네트워크 적합성:** 현재 설계가 로컬 전용(비복제)인 만큼, 서버와 클라이언트의 각 월드에 자연스럽게 독립적인 인스턴스가 생성되어 의도에 완벽히 부합합니다.
        4.  **의존성 단순화 및 오버헤드 제거:** 어디서든 `GetWorld()->GetSubsystem<UFloatingDamageSubsystem>()`이라는 표준 방식으로 접근할 수 있어 가독성이 향상됩니다. 또한, `UObject` 기반이므로 `AActor`가 가지는 불필요한 트랜스폼이나 씬 컴포넌트 등의 오버헤드를 제거할 수 있습니다.
