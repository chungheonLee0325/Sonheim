# 6.3. 통합 상호작용 시스템 (Unified Interaction System)

## 6.3.1. 설계 목표

상호작용 시스템은 플레이어가 월드와 소통하는 가장 기본적인 창구입니다. 아이템 줍기, 상자 열기, 자원 채집 등 다양한 상호작용을 일관되고, 유연하며, 확장 가능하게 만드는 것을 목표로 합니다.

1.  **통합된 상호작용 모델:** 모든 상호작용을 "상호작용한다"는 단일한 개념 아래 일관된 방식으로 처리합니다.
2.  **플레이어와 오브젝트의 분리 (Decoupling):** 플레이어는 상호작용 대상이 '제작대'인지 '상자'인지 알 필요 없이, 단지 '상호작용 가능하다'는 사실만 알면 되도록 시스템을 분리합니다.
3.  **손쉬운 확장성:** 새로운 종류의 상호작용 오브젝트(예: 레버, NPC 대화)를 플레이어 코드를 전혀 수정하지 않고 시스템에 즉시 통합할 수 있어야 합니다.

---

## 6.3.2. 아키텍처: 두 가지 방식의 의도적 분리

Sonheim의 상호작용 시스템은 단 하나의 만능 해결책을 고집하지 않고, 상호작용의 성격에 따라 두 가지 다른 기술을 의도적으로 선택하여 적용했습니다.

#### 1. 인터페이스 기반 상호작용 (for 'Use' Actions)

*   **목적:** 아이템 줍기, 문 열기, 상자 사용 등, 대상의 종류와 관계없이 통일된 행위를 유발하는 경우에 사용됩니다.
*   **핵심:** `IInteractableInterface`라는 '계약'을 통해, 플레이어의 `UInteractionComponent`가 상대방이 누구인지 전혀 모르는 상태에서 상호작용을 요청하고, 각 객체는 약속된 `Interact` 함수 내에 자신만의 고유한 로직을 수행합니다.

#### 2. 데미지 시스템 기반 상호작용 (for 'Harvest' Actions)

*   **목적:** 나무, 광석 등, 도구를 사용한 공격 행위를 통해 대상의 상태(HP)를 점진적으로 변화시키고 그 과정에서 결과를 얻는 '채집'이나 '파괴'에 사용됩니다.
*   **핵심:** 별도의 채집 시스템을 구축하는 대신, 이미 잘 구축된 전투의 `TakeDamage` 파이프라인을 재활용하여 개발 효율성과 직관성을 높입니다.

---

## 6.3.3. 핵심 구현 1: 인터페이스 기반 상호작용

이 방식은 **탐지자(`UInteractionComponent`)**, **계약(`IInteractableInterface`)**, **구현체(상호작용 객체)** 세 요소로 동작합니다.

1.  **탐지 (`UInteractionComponent`):** 플레이어에 부착된 이 컴포넌트는 주기적으로 전방을 탐색하여 `IInteractableInterface`를 구현한 객체를 찾습니다. 또한, 대상의 `GetHoldDuration` 함수를 호출하여 '단순 누름'과 '길게 누름(Hold)' 상호작용을 모두 지원하는 타이머 로직을 내장하고 있습니다.

2.  **실행 (`UInteractionComponent`):** 플레이어가 상호작용 키를 누르면, `Server_TryInteract` RPC를 통해 서버에 요청을 보냅니다. 서버는 유효성을 검사한 후, 탐지된 객체의 `Interact` 함수를 호출합니다. 컴포넌트는 상대가 누구인지 전혀 신경 쓰지 않고, 그저 'Interact'라는 약속된 함수만 호출할 뿐입니다.

3.  **구현 (e.g., `ACraftingStation`):** `ACraftingStation`은 `IInteractableInterface`를 구현하고, `Interact_Implementation` 함수 내부에 제작 UI를 여는 자신만의 고유 로직을 캡슐화합니다. 이를 통해 새로운 상호작용 객체를 추가할 때 플레이어 코드를 전혀 수정할 필요가 없습니다.

---

## 6.3.4. 핵심 구현 2: 데미지 시스템 기반 상호작용

자원 오브젝트(`ABaseResourceObject`)는 `AActor`로부터 상속받은 `TakeDamage` 함수를 오버라이드하여, 공격받을 때마다 자원을 생성하는 로직을 구현합니다.

```cpp
// BaseResourceObject.cpp
float ABaseResourceObject::TakeDamage(float Damage, ..., AActor* DamageCauser)
{
    // ... 서버 권위 확인 ...

    float PreviousHP = HealthComponent->GetHP();
    HealthComponent->ModifyHP(-ActualDamage);
    float CurrentHP = HealthComponent->GetHP();

    // 체력이 일정 임계값(Threshold)을 넘어설 때마다 자원을 스폰
    float ThresholdHP = HealthComponent->GetMaxHP() * dt_ResourceObject->DamageThresholdPct;
    int32 PreviousHPSegment = FMath::FloorToInt(PreviousHP / ThresholdHP);
    int32 CurrentHPSegment = FMath::FloorToInt(CurrentHP / ThresholdHP);

    if (CurrentHPSegment < PreviousHPSegment)
    {
        SpawnPartialResources(PreviousHPSegment - CurrentHPSegment);
    }

    // ... 체력이 0이 되면 파괴 ...
    return ActualDamage;
}
```
이 방식의 장점은, 전투와 채집이 동일한 `TakeDamage` 파이프라인을 공유하므로, 무기의 `EAttackType`(타격, 참격 등)에 따라 자원에 가하는 데미지를 다르게 하는 '약점 시스템'을 전투와 동일한 방식으로 손쉽게 구현할 수 있다는 것입니다.

## 6.3.5. 구현 경험 및 리팩토링 제안

#### 문제: `TakeDamage` 로직의 중복

*   **상황:** 피해를 받을 수 있는 `ABaseAreaObject`(플레이어, 몬스터)와 `AResourceObject`(자원)는 서로 상속 관계가 아니므로, "서버에서만 데미지를 처리하고, 체력이 0 이하일 때 죽거나 파괴된다"는 핵심 로직이 각 클래스에 거의 동일하게 중복 작성되어 있었습니다.
*   **문제점:** 코드 중복은 유지보수성을 크게 저해합니다. 데미지 계산 공식을 변경할 때 양쪽을 모두 수정해야 하므로 실수가 발생하기 쉽습니다.

#### 해결 방안: `HealthComponent`의 역할 강화

*   **제안:** 이 문제를 해결하는 가장 이상적인 방법은, 데미지 처리 로직을 **`HealthComponent` 한 곳에 중앙화**하는 것입니다.
    1.  `HealthComponent`가 `TakeDamage` 이벤트를 직접 받도록 합니다.
    2.  컴포넌트 내부에서 체력을 감소시키고, 체력이 0이 되면 `OnHealthZero`와 같은 델리게이트를 브로드캐스트합니다.
    3.  `ABaseAreaObject`와 `AResourceObject`는 이 델리게이트에 자신의 `OnDestroyed` 함수를 바인딩하기만 하면 됩니다.
*   **기대 효과:** 이 리팩토링을 통해 코드 중복이 완벽하게 제거되고, 데미지 관련 로직을 수정해야 할 때 `HealthComponent` 단 한 곳만 수정하면 되므로 프로젝트의 안정성과 확장성이 크게 향상됩니다.
