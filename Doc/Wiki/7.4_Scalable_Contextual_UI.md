# 7.4. 확장 가능한 컨텍스트 UI

> ### "UI는 당신의 존재를 모릅니다": 각자 자신의 UI를 책임지는 인터페이스 기반 컨텍스트 UI 아키텍처
> 
> *   **책임의 역전 (Inversion of Responsibility):** UI 위젯(`DetectWidget`)이 상호작용 대상을 `Cast`하며 분기하는 대신, 각 상호작용 대상(`ABaseItem`, `ACraftingStation` 등)이 `UInteractableInterface`를 구현하고 **자신만의 `DetectWidget`을 직접 소유 및 관리**합니다.
> *   **완벽한 분리 (Decoupling via Interface):** 플레이어의 `InteractionComponent`는 대상의 구체적인 클래스를 전혀 알 필요 없이, 오직 `UInteractableInterface`라는 "약속"에만 의존하여 "너는 감지되었다"(`OnDetected`)는 신호만 보냅니다.
> *   **궁극의 확장성 (Ultimate Scalability):** 이 구조 덕분에, 새로운 상호작용 오브젝트를 추가할 때 UI 시스템 코드는 단 한 줄도 수정할 필요가 없습니다. 새로 추가된 액터가 인터페이스의 "약속"만 지키면 시스템이 즉시 확장됩니다.

## 7.4.1. 구현 기능 목록 (Feature List)

*   **동적 컨텍스트 정보:** 플레이어가 바라보는 대상에 따라 상호작용 UI의 내용(이름, 행동 지시)이 동적으로 변경됩니다.
*   **아이템 이름 표시:** 월드에 드롭된 아이템을 바라보면 해당 아이템의 이름이 표시됩니다.
*   **제작대 상태 표시:** 제작대를 바라보면, 제작 가능한 상태에서는 "레시피 선택", 제작 중일 때는 "[길게 누르기] 작업", 완성품이 있을 때는 "취득"이라는 각기 다른 텍스트가 표시됩니다.
*   **실시간 홀드 피드백:** "작업"이나 "취소"와 같이 길게 눌러야 하는 상호작용의 경우, 진행률이 원형 프로그레스 바로 실시간 표시됩니다.
*   **시각적 하이라이트:** 감지된 상호작용 대상은 시각적인 하이라이트 효과가 적용되어 플레이어가 명확하게 인지할 수 있습니다.

---

## 7.4.2. 기술 상세 (Technical Deep Dive)

### 7.4.2.1. Why: 책임의 역전(Inversion of Responsibility)이 왜 필요한가?

월드에는 플레이어가 상호작용할 수 있는 수많은 오브젝트가 존재하며, 이들을 바라볼 때 나타나는 UI는 각 오브젝트의 상황에 맞는 정확한 정보를 표시해야 합니다. 만약 UI 위젯이 `if (Target->IsA<ABaseItem>()) ... else if (Target->IsA<ACraftingStation>()) ...` 와 같이 모든 대상을 하드코딩하여 분기 처리한다면, 새로운 종류의 오브젝트가 추가될 때마다 이 위젯의 코드는 계속해서 수정되어야만 합니다. 이는 유지보수의 악몽으로 이어집니다.

이 문제를 해결하기 위해, **정보 표시의 책임을 UI가 아닌 각 상호작용 대상에게 역전**시켰습니다. UI는 "정보를 표시한다"는 자신의 역할에만 집중하고, 각 게임플레이 오브젝트는 "자신이 어떤 정보를 표시할지 결정한다"는 역할에만 집중하도록 하여, 시스템을 완벽하게 분리하고 확장성을 극대화하는 것을 목표로 했습니다.

### 7.4.2.2. How: 인터페이스를 통한 아키텍처 구현

이 아키텍처의 핵심은, UI나 상호작용 컴포넌트가 대상의 구체적인 클래스를 확인하는 대신, **`UInteractableInterface`** 라는 공통된 "약속"을 구현했는지 여부만 확인하는 것입니다.

```mermaid
flowchart TD
    A[InteractionComponent<br>Detects Target Actor] --> B{Target implements<br>UInteractableInterface?};
    B -- Yes --> C[\"Calls Interface Function<br>OnDetected(true)\"];
    
    subgraph "Self-Managed UI by Providers"
        C -- Trigger --> E[ABaseItem: OnDetected()<br><em>Shows its own widget with item name</em>];
        C -- Trigger --> F["ACraftingStation: OnDetected()<br><em>Shows its own widget with current state</em>"];
    end

    B -- No --> G[No Interaction];
```

#### 7.4.2.2.1. 1단계: 약속의 정의 (The Contract)

가장 먼저, 모든 상호작용 가능한 객체들이 반드시 지켜야 할 공통된 약속, 즉 `UInteractableInterface`를 정의합니다. 이 인터페이스는 컨텍스트 UI가 필요로 하는 모든 정보(표시할 이름, 감지 상태 등)를 얻기 위한 함수들을 `BlueprintNativeEvent`로 선언합니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/GameObject/InteractableInterface.h#L31)
```cpp
// Source/Sonheim/GameObject/InteractableInterface.h
class SONHEIM_API IInteractableInterface
{
    GENERATED_BODY()
public:
    // 감지됨/해제됨 알림
    UFUNCTION(BlueprintNativeEvent, BlueprintCallable, Category = "Interaction")
    void OnDetected(bool bDetected);

    // 표시할 이름
    UFUNCTION(BlueprintNativeEvent, BlueprintCallable, Category = "Interaction")
    FString GetInteractionName() const;
    
    // ... 기타 상호작용 함수들 ...
};
```

#### 7.4.2.2.2. 2단계: 정보 소비자 (The Consumer)

`InteractionComponent`는 주기적으로 전방을 탐색하여 상호작용 가능한 대상을 찾습니다. 이 때, 대상의 구체적인 클래스를 확인하는 대신, `UInteractableInterface`를 구현했는지 여부만 확인하고 `OnDetected` 함수를 호출하여 "네가 감지되었다"는 신호만 보내줍니다. 소비자는 정보의 내용이나 UI의 존재 자체를 전혀 알 필요가 없습니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/AreaObject/Player/Utility/InteractionComponent.cpp#L198)
```cpp
// Source/Sonheim/AreaObject/Player/Utility/InteractionComponent.cpp
void UInteractionComponent::UpdateInteractable(AActor* NewTarget, float Distance)
{
    if (NewTarget != CurrentInteractable)
    {
        // 1. 이전 대상에게는 감지가 끝났음을 알린다.
        if (CurrentInteractable)
        {
            IInteractableInterface::Execute_OnDetected(CurrentInteractable, false);
        }

        CurrentInteractable = NewTarget;

        // 2. 새로운 대상에게는 감지가 시작되었음을 알린다.
        if (CurrentInteractable)
        {
            IInteractableInterface::Execute_OnDetected(CurrentInteractable, true);
        }
    }
}
```

#### 7.4.2.2.3. 3단계: 정보 제공자 (The Providers)

`UInteractableInterface`를 구현한 각 액터는, **자신만의 `UDetectWidgetComponent`를 멤버로 소유**하고, 동일한 인터페이스 함수를 자신만의 상황과 데이터에 맞게 **재정의(Override)**하여 구체적인 정보를 제공하고 UI를 직접 관리합니다.

*   **`ABaseItem`의 경우:** 자신의 아이템 데이터 테이블에서 **정적인** `ItemName`을 찾아 반환하고, `OnDetected`가 호출되면 자신의 위젯을 켜고 끕니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/GameObject/Items/BaseItem.cpp#L462)
```cpp
// Source/Sonheim/GameObject/Items/BaseItem.cpp
void ABaseItem::OnDetected_Implementation(bool bDetected)
{
    // ...
    if (DetectWidgetComponent)
    {
        DetectWidgetComponent->SetVisibility(bDetected);
    }
    // ...
}

FString ABaseItem::GetInteractionName_Implementation() const
{
    return dt_ItemData ? dt_ItemData->ItemName.ToString() : FString("아이템");
}
```

*   **`ACraftingStation`의 경우:** 자신의 내부 상태 변수를 확인하여, **동적인** 컨텍스트에 맞는 텍스트를 반환하고, `OnDetected`가 호출되면 자신의 위젯을 켜고 끕니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/GameObject/Buildings/Crafting/CraftingStation.cpp#L175)
```cpp
// Source/Sonheim/GameObject/Buildings/Crafting/CraftingStation.cpp
FString ACraftingStation::GetInteractionName_Implementation() const
{
    if (CompletedToCollect > 0) return TEXT("취득");
    if (bHasActiveWork) return TEXT("[길게 누르기] 작업");
    return TEXT("레시피 선택");
}
```
위 코드는 이 아키텍처의 강력함을 명확히 보여줍니다. `ACraftingStation`은 플레이어의 동일한 상호작용(F키)에 대해, 자신의 내부 상태에 따라 전혀 다른 세 가지 행동 중 하나를 수행하며, UI는 다음에 일어날 행동을 정확히 안내하는 역할을 합니다.

1.  **`CompletedToCollect > 0` (수령할 완성품이 있을 때):** UI는 **"취득"**을 표시하고, F키는 완성된 아이템을 즉시 획득하는 `ServerCollectAll` 함수를 호출합니다.
2.  **`bHasActiveWork` (진행 중인 작업이 있을 때):** UI는 **"[길게 누르기] 작업"**을 표시하고, F키를 길게 누르면 제작을 지원하여 진행도를 올리는 `ServerAddWork` 함수가 호출됩니다.
3.  **그 외의 경우 (아무 작업도 없을 때):** UI는 **"레시피 선택"**을 표시하고, F키는 제작 UI를 열어 새로운 제작을 시작하는 `ServerRequestOpenUI` 함수를 호출합니다.

`InteractionComponent`는 이 복잡한 상태 로직을 전혀 알 필요가 없습니다. 그저 `GetInteractionName`이라는 약속된 질문을 던질 뿐이며, `ACraftingStation`이 자신의 상태에 맞는 올바른 대답을 돌려주어, 플레이어가 다음에 할 행동을 정확히 인지하도록 돕습니다. 제작 시스템의 더 자세한 동작 방식은 [[6.5 제작 시스템|6.5_Crafting_System]] 문서에서 확인할 수 있습니다.

### 7.4.2.3. What: 설계의 결과 (The Result)

*   **완벽한 분리 (Decoupling):** `InteractionComponent`와 `DetectWidget`은 `ABaseItem`이나 `ACraftingStation`의 존재 자체를 알 필요가 없으며, 오직 `UInteractableInterface`라는 약속에만 의존합니다. 이 덕분에 UI 시스템과 게임플레이 오브젝트 시스템은 서로에게 아무런 영향을 주지 않고 독립적으로 개발 및 수정될 수 있습니다.
*   **엄청난 확장성 (Massive Scalability):** 미래에 '잠긴 문', 'NPC', '레버 스위치' 등 새로운 종류의 상호작용 오브젝트를 수백 개 추가하더라도, 그 오브젝트들이 `UInteractableInterface`를 구현하고 `OnDetected`와 `GetInteractionName` 함수를 올바르게 재정의하기만 한다면, `InteractionComponent`나 `DetectWidget`의 코드는 **단 한 줄도 수정할 필요 없이** 모든 오브젝트와 완벽하게 상호작용할 수 있습니다.
*   **명확한 역할 분담:** 각 상호작용 객체는 "자신이 어떤 이름으로 불릴지, 언제 UI를 표시할지"를 스스로 결정합니다. 이는 코드의 가독성과 유지보수성을 극대화합니다.
