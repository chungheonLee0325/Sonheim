# 2.1. 데이터 주도 설계 (Data-Driven Design)

## 2.1.1. 설계 철학: "코드는 로직을, 데이터는 콘텐츠를"

Sonheim 프로젝트의 가장 핵심적인 설계 원칙은 **데이터 주도 아키텍처(Data-Driven Architecture)**입니다. 이는 게임의 '내용'(아이템, 스킬, 몬스터 스탯 등)을 코드에서 완전히 분리하여, 기획자가 프로그래머의 개입이나 재컴파일 없이 데이터 수정만으로 게임의 밸런스와 콘텐츠를 자유롭게 확장할 수 있도록 만드는 **"No-Compile" 콘텐츠 파이프라인** 구축을 목표로 합니다.

이러한 설계는 다음과 같은 명확한 목표를 달성하기 위해 채택되었습니다.

1.  **빠른 이터레이션과 협업:** 개발 및 밸런싱 속도를 극적으로 향상시키고, 엔지니어와 기획자 간의 역할을 명확히 분담하여 협업 효율을 극대화합니다.
2.  **로직과 콘텐츠의 분리:** 게임 로직("어떻게 동작하는가")과 게임 콘텐츠("무엇을 사용하는가")를 명확하게 분리하여 코드의 가독성과 유지보수성을 향상시킵니다.
3.  **중앙화된 데이터 관리:** 게임의 모든 핵심 데이터를 `GameInstance`라는 단일 지점에서 로드하고 캐싱하여 데이터 접근 경로를 일원화하고, 데이터의 일관성을 보장합니다.

## 2.1.2. 데이터 아키텍처 및 흐름

Sonheim의 데이터 주도 설계는 **정의(Define) → 저장 및 로드(Store & Load) → 제공 및 사용(Provide & Use)**이라는 세 가지 명확한 단계로 구현됩니다.

```mermaid
graph TD  
    A[CSV Files\<br/>(Items.csv, Recipes.csv, ...)] -->|Import| B(Unreal Editor\<br/>UDataTable Assets)  
    B -->|Load on Init| C(USonheimGameInstance)  
    C -->|Get Data API| D[Inventory System]  
    C -->|Get Data API| E[Crafting System]  
    C -->|Get Data API| F[Monster System]
```

#### 1단계: 데이터의 '설계도' 정의 (Define - `SonheimGameType.h`)
모든 데이터는 그 형태(구조)가 먼저 C++ 코드로 명확하게 정의되어야 합니다. [`SonheimGameType.h`](https://github.com/chungheonLee0325/Sonheim/blob/main/Source/Sonheim/ResourceManager/SonheimGameType.h) 파일은 이 프로젝트의 모든 데이터 구조체(`USTRUCT`)를 정의하는 **중앙 데이터 명세서** 역할을 합니다. 이 구조체들은 `FTableRowBase`를 상속받아 데이터 테이블의 행으로 사용될 수 있음을 명시합니다.

```cpp
// SonheimGameType.h - 아이템 데이터 구조체 예시
USTRUCT(BlueprintType)
struct FItemData : public FTableRowBase
{
    GENERATED_BODY()

public:
    UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Data")
    int32 ItemID;

    UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Data")
    FText ItemName;

    UPROPERTY(EditAnywhere, BlueprintReadWrite, Category = "Data")
    UTexture2D* ItemIcon;

    // ... 기타 아이템 관련 데이터
};
```

#### 2단계: 데이터의 '중앙 허브' 구축 (Store & Load - `USonheimGameInstance`)
게임이 시작되면, [`USonheimGameInstance`](https://github.com/chungheonLee0325/Sonheim/blob/main/Source/Sonheim/GameManager/SonheimGameInstance.h)는 `Init()` 함수를 통해 모든 데이터 테이블(`.csv`) 파일을 읽어들여, 각 데이터를 `TMap` 자료구조에 저장하여 메모리에 캐싱합니다. `GameInstance`는 게임 세션 내내 유지되는 싱글톤 객체이므로, 이 `TMap`이 바로 게임 세션 내내 유지되는 **인메모리 데이터베이스(In-Memory Database)** 역할을 수행합니다.

```cpp
// SonheimGameInstance.h - 데이터 테이블을 캐싱할 TMap 변수들
UCLASS()
class SONHEIM_API USonheimGameInstance : public UGameInstance
{
    GENERATED_BODY()

public:
    // ...
    FAreaObjectData* GetDataAreaObject(int AreaObjectID);
    FItemData* GetDataItem(int ItemID);

protected:
    virtual void Init() override; // 이 함수에서 실제 데이터 테이블을 로드하여 TMap을 채웁니다.

private:
    UPROPERTY()
    TMap<int32, FItemData> dt_Item;
    // ... 다른 데이터 TMap들
};
```

#### 3단계: 데이터의 '표준 API' 제공 (Provide & Use)
`GameInstance`는 `GetDataItem(ItemID)`와 같이, 게임 내 다른 시스템들이 중앙 데이터베이스에 안전하고 쉽게 접근할 수 있는 **표준화된 API**를 제공합니다. 모든 데이터는 게임 시작 시 `TMap`에 캐시되었으므로, 이 함수는 `int32` 타입의 ID를 키로 사용하여 메모리에서 데이터를 즉시 찾아 반환하여 매번 데이터 테이블을 검색하는 비용을 없앱니다.

```cpp
// SonheimGameInstance.cpp - GetDataItem 함수 구현 예시
FItemData* USonheimGameInstance::GetDataItem(int ItemID)
{
    // Init()에서 미리 캐시해 둔 TMap에서 데이터를 바로 찾아 반환합니다.
    if (FItemData* data = dt_Item.Find(ItemID))
    {
        return data;
    }

    return nullptr;
}
```

이렇게 얻어진 데이터는 게임 시스템 곳곳에서 사용됩니다. 예를 들어, `AAreaObject`는 자신의 `BeginPlay`에서 `GameInstance`로부터 자신의 데이터를 가져온 뒤, 보유 스킬 ID 목록을 `USonheimSkillComponent`에 전달하여 스킬을 초기화합니다.

```cpp
// AreaObject.cpp - 데이터 사용 예시
void AAreaObject::BeginPlay()
{
    Super::BeginPlay();

    // 1. GameInstance에서 자신의 AreaObjectData를 가져옴
    dt_AreaObject = m_GameInstance->GetDataAreaObject(m_AreaObjectID);
    if (!dt_AreaObject) return;

    // 2. 데이터에 정의된 스킬 ID 목록을 SkillComponent에 전달하여 초기화 요청
    if (m_SkillComponent)
    {
        m_SkillComponent->InitializeOwnedSkills(dt_AreaObject->SkillList);
    }
}
```

## 2.1.3. 실제 적용 가이드: 신규 아이템 추가하기

이 아키텍처 하에서 기획자는 다음과 같은 과정으로 C++ 코드 수정 없이 새로운 아이템을 추가할 수 있습니다.

1.  **데이터 테이블 열기**: 언리얼 에디터에서 `Content/Data/DT_Items` 데이터 테이블 애셋을 엽니다.
2.  **새로운 행 추가**: `Add` 버튼을 눌러 새 행을 추가하고, 행 이름(Row Name)으로 아이템의 고유 ID(예: `1001`)를 입력합니다.
3.  **데이터 입력**: 새로 추가된 행의 각 컬럼에 아이템의 속성(이름, 설명, 아이콘, 스탯 등)을 기획에 맞게 채워 넣습니다.
4.  **저장 및 테스트**: 데이터 테이블을 저장하고 게임을 실행하여, 콘솔 명령 등으로 해당 아이템이 올바르게 적용되는지 확인합니다.

## 2.1.4. 고급 고려사항 및 개선 방안

#### 1. 데이터 무결성 확보: 데이터 유효성 검증 (Data Validation)
*   **문제점**: 프로젝트가 커지면서 데이터 간의 참조 관계가 복잡해질 경우, 제작 레시피에 필요한 재료의 ID가 실수로 아이템 테이블에서 삭제되는 등 데이터 오류가 발생할 위험이 있습니다.
*   **개선 방안**: `GameInstance::Init()` 단계에서 **데이터 유효성 검증 로직**을 추가합니다. 예를 들어, 모든 제작 레시피를 순회하며 레시피에 사용된 ItemID가 실제로 아이템 데이터 테이블에 존재하는지 확인하고, 존재하지 않을 경우 명확한 에러 로그를 출력하도록 하여 데이터 오류를 개발 단계 초기에 발견하고 수정할 수 있도록 시스템을 개선합니다.

#### 2. 성능 및 협업 효율성: 데이터 에셋(`UDataAsset`) 혼용
*   **문제점**: `UDataTable`은 모든 데이터를 메모리에 로드하며, 여러 사람이 동시에 작업할 때 버전 관리 시스템에서 충돌이 발생할 수 있습니다.
*   **개선 방안**: 아이템이나 스킬처럼 개수가 많고 개별적인 데이터는 별도의 **데이터 에셋(`UDataAsset`)** 파일로 만드는 것을 고려할 수 있습니다. 데이터 테이블은 이 데이터 에셋들을 가리키는 역할만 수행합니다.
*   **기대 효과**: 필요한 데이터 에셋만 선택적으로 로드하여 메모리 사용량을 최적화하고, 각 데이터가 개별 파일로 존재하므로 여러 사람이 동시에 다른 데이터를 작업할 때 버전 관리 충돌을 최소화할 수 있습니다.
