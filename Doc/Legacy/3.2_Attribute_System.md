# 3.2. 어트리뷰트 시스템: 모든 능력치의 기반

> ### 독립적인 기능 컴포넌트와 이벤트 기반 델리게이트를 통해, 모든 캐릭터의 핵심 능력치(HP, 스태미나 등)를 관리하는 재사용 가능하고 확장성 높은 속성 시스템을 구축했습니다.
> 
> *   **모듈성:** HP, 스태미나, 상태이상, 레벨 등 각 속성을 독립적인 `ActorComponent`로 구현하여, 필요한 개체에 원하는 기능만 선택적으로 부착할 수 있도록 설계했습니다.
> *   **이벤트 기반 구조:** 각 컴포넌트는 자신의 상태가 변경될 때 `Delegate`를 통해 외부에 변경 사실을 "방송"합니다. UI와 같은 외부 시스템은 이 방송을 "구독"하기만 하면, 속성 값의 변경을 감지하고 스스로를 업데이트할 수 있어 시스템 간의 결합도를 극적으로 낮췄습니다.
> *   **서버 권위:** 모든 속성 값의 변경은 서버에서만 권위있게 처리되며, 그 결과는 `ReplicatedUsing`을 통해 클라이언트에 효율적으로 복제되어 모든 플레이어에게 일관된 상태를 보장합니다.

---

## 3.2.1. 구현 기능 목록 (Feature List)

이 시스템은 Sonheim의 모든 캐릭터(`AAreaObject`)에게 다음과 같은 공통 속성 관리 기능을 제공합니다.

*   **핵심 생명력 (Health & Stamina)**
    *   서버 권위 하에 모든 캐릭터의 체력과 스태미나를 안전하게 관리합니다.
    *   체력이나 스태미나가 변경되면, UI가 이를 자동으로 감지하여 화면의 HP/Stamina 바를 스스로 업데이트합니다.
    *   스태미나는 사용 후 일정 시간이 지나면 자동으로 회복됩니다.

*   **상태 이상 (Condition)**
    *   비트마스크(Bitmask)를 활용하여, 기절, 무적, 사망 등 수십 가지의 상태 이상을 단 하나의 변수로 효율적으로 관리합니다.
    *   `AddCondition` 함수에 지속시간(Duration)을 함께 전달하면, 해당 시간이 지난 후 상태 이상이 자동으로 해제되는 시간제한 효과를 지원합니다.

*   **성장 및 진척 (Level)**
    *   데이터 테이블에 정의된 경험치 테이블에 따라 캐릭터의 레벨과 경험치를 관리합니다.
    *   레벨이 오르면, 캐릭터의 기본 스탯(HP, 공격력 등)이 자동으로 증가하고, 추가로 스탯 포인트를 지급합니다.
    *   캐릭터가 사냥당했을 때, 자신을 사냥한 대상에게 제공할 경험치 양(`RewardHuntExp`)을 결정합니다.

## 3.2.2. 기술 상세 (Technical Deep Dive)

### 3.2.2.1. 아키텍처: 공용 컴포넌트와 동적 보너스의 분리

Sonheim의 속성 시스템은 두 개의 큰 축으로 구성됩니다.

1.  **공용 속성 컴포넌트 (본 문서):** `AAreaObject`에 기본으로 부착되어 모든 캐릭터가 공통으로 가지는 핵심 속성(`Health`, `Stamina`, `Condition`, `Level`)을 관리합니다. 이 컴포넌트들의 초기값은 대부분 데이터 테이블(`dt_AreaObject`)에 의해 결정됩니다.
2.  **동적 스탯 보너스 시스템:** 플레이어의 장비, 버프, 스킬 레벨 등 수시로 변하는 요인에 의해 동적으로 계산되는 스탯(공격력, 방어력 등)은 별도의 `UStatBonusComponent`가 담당합니다. 이 내용은 **[[4.3 스탯 시스템|4.3_Stat_System]]** 문서에서 상세히 다룹니다.

이처럼 역할과 복잡도에 따라 시스템을 분리함으로써, 단순한 몬스터는 가벼운 공용 컴포넌트만 사용하고, 복잡한 플레이어 캐릭터는 여기에 스탯 보너스 시스템을 추가로 조합하는 유연한 구조를 완성했습니다.

### 3.2.2.2. 핵심 구현 1: 이벤트 기반 통신 패턴 (HealthComponent)

이 시스템의 핵심은 `Delegate`를 이용한 이벤트 기반 통신입니다. `HealthComponent`를 예로 들면, 서버에서 HP가 변경되었을 때, 이 사실이 어떻게 클라이언트의 UI까지 전달되는지는 다음의 흐름을 따릅니다.

1.  **서버의 값 변경 및 델리게이트 호출:** 서버의 `ModifyHP` 함수는 HP 값을 변경한 후, 즉시 `OnHealthChanged` 델리게이트를 호출(Broadcast)합니다. 서버에 존재하는 다른 시스템은 이 델리게이트에 자신의 함수를 미리 바인딩해두는 것만으로 HP 변경에 즉시 반응할 수 있습니다.

2.  **클라이언트로의 자동 복제 및 OnRep 호출:** `m_HP` 변수는 `ReplicatedUsing = OnRep_HP`로 지정되어, 서버에서 값이 바뀔 때마다 클라이언트의 `OnRep_HP` 함수가 자동으로 호출됩니다.

3.  **클라이언트에서의 델리게이트 호출:** `OnRep_HP` 함수는 클라이언트에 있는 `OnHealthChanged` 델리게이트를 호출합니다. 클라이언트의 HP 바 UI 위젯은 생성될 때 자신의 "HP를 갱신하는 함수"를 이 델리게이트에 미리 바인딩해두었기 때문에, 컴포넌트의 내부를 전혀 알지 못해도 HP 변경에 완벽하게 반응하여 스스로를 업데이트할 수 있습니다.

> [View on GitHub (HealthComponent.h)](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/AreaObject/Attribute/HealthComponent.h#L7)
> [View on GitHub (HealthComponent.cpp)](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/AreaObject/Attribute/HealthComponent.cpp#L29)
```cpp
// HealthComponent.h
// 1. 델리게이트 선언
DECLARE_DYNAMIC_MULTICAST_DELEGATE_ThreeParams(FOnHealthChangedDelegate, float, CurrentHP, float, Delta, float, MaxHP);

// ...
UPROPERTY(BlueprintAssignable) // UI 등에서 바인딩 가능
FOnHealthChangedDelegate OnHealthChanged;

// 2. 변수 복제 설정
UPROPERTY(ReplicatedUsing = OnRep_HP)
float m_HP;

// HealthComponent.cpp
// 3. 서버에서 값 변경 및 델리게이트 직접 호출
void UHealthComponent::ModifyHP(float Delta)
{
    if (GetOwnerRole() != ROLE_Authority) return;
    // ... 값 변경 로직 ...
    OnHealthChanged.Broadcast(m_HP, Delta, m_HPMax); // 서버에서 즉시 호출
}

// 4. 클라이언트에서 OnRep을 통해 델리게이트 호출
void UHealthComponent::OnRep_HP(float OldHP)
{
    float Delta = m_HP - OldHP;
    OnHealthChanged.Broadcast(m_HP, Delta, m_HPMax); // 클라이언트 UI가 반응할 수 있도록 호출
}
```

### 3.2.2.3. 핵심 구현 2: 비트마스크를 이용한 상태 관리 (ConditionComponent)

`ConditionComponent`는 `Dead`, `Invincible`, `Stunned` 등 수많은 상태 이상을 `uint32 ConditionFlags` 라는 단일 정수 변수와 비트 연산을 통해 관리합니다. 이는 여러 개의 `bool` 변수를 사용하는 것보다 훨씬 효율적입니다.

*   **상태 추가:** `AddCondition` 함수는 `OR` 연산(`|=`)을 사용하여 특정 상태에 해당하는 비트를 `1`로 만듭니다.
*   **상태 제거:** `RemoveCondition` 함수는 `AND` 연산(`&=`)과 `NOT` 연산(`~`)을 조합하여 특정 상태의 비트만 `0`으로 만듭니다.
*   **상태 확인:** `HasCondition` 함수는 `AND` 연산(`&`)을 통해 특정 상태의 비트가 `1`인지 아닌지를 확인합니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/AreaObject/Attribute/ConditionComponent.cpp#L17)
```cpp
// ConditionComponent.cpp
void UConditionComponent::AddCondition(EConditionBitsType Condition, float Duration)
{
    if (GetOwnerRole() != ROLE_Authority) return;

    // OR 연산으로 해당 상태 비트를 1로 설정
    ConditionFlags |= static_cast<uint32>(Condition);

    // ... 시간제한 로직 ...
}

bool UConditionComponent::HasCondition(EConditionBitsType Condition) const
{
    // AND 연산으로 해당 비트가 1인지 확인
    return (ConditionFlags & static_cast<uint32>(Condition)) != 0;
}
```

### 3.2.2.4. 핵심 구현 3: 데이터 기반 레벨 관리 (LevelComponent)

`LevelComponent`는 레벨업에 필요한 경험치와 같은 핵심 데이터를 코드에 하드코딩하는 대신, `GameInstance`로부터 레벨 데이터 테이블(`dt_Level`)을 받아와 사용합니다. `AddExp` 함수는 경험치를 추가한 후, 현재 경험치가 데이터 테이블에 정의된 `ExpToNextLevel`보다 많으면 `HandleLevelUp` 함수를 호출하여 레벨업을 진행합니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/AreaObject/Attribute/LevelComponent.cpp#L45)
```cpp
// LevelComponent.cpp
void ULevelComponent::AddExp(int32 ExpAmount)
{
    if (GetOwnerRole() != ROLE_Authority || IsMaxLevel()) return;

    CurrentExp += ExpAmount;
    OnExperienceChanged.Broadcast(CurrentExp, ExpToNextLevel, ExpAmount);

    // 데이터 테이블의 필요 경험치와 비교하여 레벨업 처리
    while (!IsMaxLevel() && CurrentExp >= ExpToNextLevel)
    {        
        HandleLevelUp();
    }
}

void ULevelComponent::HandleLevelUp()
{
    // ... 
    CurrentLevel++;
    
    // 다음 레벨의 필요 경험치를 데이터 테이블에서 가져옴
    if(dt_Level->Find(CurrentLevel) != nullptr)
    {
        ExpToNextLevel = dt_Level->Find(CurrentLevel)->ExpToNextLevel;
    }
    // ...
}
```

## 3.2.4. 회고 및 개선점

### 문제점: 시간제한 상태 이상의 중첩 불가
현재 `ConditionComponent`는 `TMap<EConditionBitsType, FTimerHandle>`을 사용하여 시간제한 상태 이상을 관리합니다. 이 구조는 특정 타입의 상태 이상에 대해 단 하나의 타이머만 가질 수 있어, 동일한 상태 이상(예: 5초 기절 효과를 받은 직후, 다른 적으로부터 2초 기절 효과를 추가로 받는 경우)이 중첩될 때 마지막에 적용된 타이머가 이전 타이머를 덮어쓰는 **"마지막 효과 우선(Last-one-wins)"** 문제를 야기합니다. 이 경우, 5초 기절이 2초 만에 풀리는 심각한 버그가 발생할 수 있습니다.

### 개선 방안: GUID 기반의 개별 타이머 관리
이 문제를 근본적으로 해결하기 위해, `AddCondition` 함수가 상태 이상을 적용할 때마다 고유한 **`FGuid`**를 반환하고, 상태 이상을 제거할 때는 이 `FGuid`를 명시적으로 요구하는 방식으로 리팩토링할 수 있습니다.

*   **`TMap<EConditionBitsType, FTimerHandle>` -> `TMap<FGuid, FTimerHandle>`**
*   `AddCondition(...)` -> `FGuid AddCondition(...)`
*   `RemoveCondition(EConditionBitsType)` -> `RemoveConditionByGuid(FGuid)`

이는 `USonheimSkillComponent`가 여러 장비로부터 동일한 스킬을 부여받아도 충돌 없이 관리하는 **Grant/Revoke 시스템**에서 이미 그 안정성이 증명된 방식입니다. 이 구조를 채택하면, 여러 개의 동일한 상태 이상이 각자의 고유한 지속시간을 가지고 안전하게 공존할 수 있게 되어, 시스템의 안정성과 확장성을 크게 향상시킬 것입니다.
