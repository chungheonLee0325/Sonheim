# 6.2. 아이템 시스템 (ABaseItem)

> ### 데이터 기반 속성과 유연한 스폰 옵션으로 구현된, 네트워크에 최적화된 월드 아이템
> 
> *   **정적/동적 데이터 분리:** 아이템의 본질적인 속성(**정적 데이터**)은 데이터 테이블로, 생성되는 상황에 따른 동작 방식(**동적 데이터**)은 스폰 옵션으로 분리하여, 유지보수성과 확장성을 모두 확보했습니다.
> *   **유연한 스폰 옵션 (`FItemSpawnOptions`):** 아이템의 모든 동작 방식(자동/수동 획득, 물리 효과, 생명 주기)이 스폰 시점에 주입되는 단일 구조체에 의해 결정되며, **자주 사용하는 설정들을 템플릿화한 헬퍼 함수**를 제공하여 편의성을 극대화했습니다.
> *   **네트워크 최적화 (Net Dormancy):** 월드에 드롭된 아이템의 물리적 움직임이 멈추면 네트워크 업데이트를 완전히 중단시켜, 수백 개의 아이템이 존재해도 서버 부하를 최소화합니다.

## 6.2.1. 구현 기능 목록 (Feature List)

`ABaseItem`은 스폰 시점에 `FItemSpawnOptions` 구조체를 받아, 다음과 같은 다양한 기능 조합을 가질 수 있습니다.

*   **획득 방식 (`bRequireInteraction`, `InteractionType`)
    *   **자동 획득:** 플레이어가 아이템 근처로 다가가면 자동으로 인벤토리에 추가됩니다.
    *   **수동 획득:** 플레이어가 아이템을 직접 바라보고 상호작용해야만 획득할 수 있습니다. (즉시/홀드 방식 모두 지원)

*   **생명 주기 (`LifeTime`, `AutoPickupDelay`)
    *   **자동 파괴:** 지정된 시간이 지나면 월드에서 자동으로 사라집니다.
    *   **획득 지연:** 스폰된 후 일정 시간이 지나야만 자동 획득이 가능하도록 설정할 수 있습니다.

*   **물리 효과 (`bApplyPhysicsOnDrop`, `DropForce`)
    *   **자연스러운 드롭 연출:** 스폰될 때 랜덤한 방향으로 물리적 힘(Impulse)을 받아 자연스럽게 바닥에 흩뿌려지는 효과를 냅니다.

*   **네트워크 최적화**
    *   아이템이 물리적 움직임을 멈추고 바닥에 가만히 놓여있을 때는, 서버와의 네트워크 통신을 완전히 중단하여 서버 부하를 발생시키지 않습니다.

## 6.2.2. 기술 상세 (Technical Deep Dive)

### 6.2.2.1. 서론: `ABaseItem`이란 무엇인가? (월드에 존재하는 아이템)

Sonheim의 아이템은 두 가지 형태로 존재합니다. 하나는 `FItemData`나 `FInventoryItem`처럼 **데이터로만 존재하는 추상적인 아이템**이고, 다른 하나는 `ABaseItem`처럼 **월드에 실제로 스폰되어 물리적인 실체를 가지는 아이템**입니다.

*   **`FItemData` (설계도):** \'곡괭이\'의 이름, 아이콘, 성능 등 본질적인 정보를 담고 있는 데이터 테이블의 한 행입니다.
*   **[[`FInventoryItem`|4.2_Inventory_System]] (재고 기록):** "인벤토리에 \'곡괭이\'가 3개 있다"는 사실을 기록하는 `ItemID`와 `Count`로 이루어진 데이터입니다.
*   **`ABaseItem` (실물 제품):** 이 `FItemData`를 기반으로, 월드에 실제로 드롭되어 반짝이는 **\'곡괭이\' 그 자체**입니다. 이 클래스는 물리 효과, 충돌, 시각적 표현 등 월드와의 모든 상호작용을 담당합니다.

이 문서는 바로 이 `ABaseItem` 클래스가 데이터(`FItemData`)와 스폰 옵션(`FItemSpawnOptions`)을 받아, 월드 위에서 살아 숨 쉬는 아이템으로 완성되는지의 전체 과정을 심층적으로 분석합니다.

### 6.2.2.2. 아키텍처: 정적 데이터와 동적 데이터의 역할 분리

> **왜 데이터를 두 종류로 나누어 관리하는가?**
> 몬스터가 드롭한 \'곡괭이\'와 플레이어가 인벤토리에서 버린 \'곡괭이\'는 본질(`ItemID`, 외형, 성능)은 같지만, 생성되는 **상황적인 맥락**은 다릅니다. 전자는 자동 획득이 편리하고, 후자는 플레이어가 다시 주워야 하므로 수동 획득이 필요합니다. 
> 
> 이처럼 동일한 아이템이라도 다른 방식으로 동작해야 할 필요가 있기 때문에, 아이템의 데이터를 두 종류로 분리했습니다.

1.  **정적 데이터 (`FItemData`):** 아이템의 **본질적인 속성**을 정의합니다. 데이터 테이블로 관리하여, 모든 \'곡괭이\' 아이템이 공유하는 이름, 아이콘, 등급 등 불변의 데이터를 일관되게 유지하고 기획자가 쉽게 편집할 수 있도록 합니다.

```cpp
// Source/Sonheim/ResourceManager/SonheimGameType.h
USTRUCT(BlueprintType)
struct FItemData : public FTableRowBase
{
    GENERATED_BODY()

    UPROPERTY(EditAnywhere) int ItemID = 0;
    UPROPERTY(EditAnywhere) FText ItemName = FText::FromString("Unknown");
    UPROPERTY(EditAnywhere) UTexture2D* ItemIcon = nullptr;
    UPROPERTY(EditAnywhere) UStaticMesh* ItemMesh = nullptr;
    UPROPERTY(EditAnywhere) EItemRarity ItemRarity = EItemRarity::Common;
    // ... and many other static properties
};
```

2.  **동적 데이터 (`FItemSpawnOptions`):** 아이템이 생성되는 **상황적인 맥락**을 정의합니다. 자동/수동 획득 여부, 물리 효과, 생명 주기 등 스폰될 때 단 한 번 결정되는 일회성 속성들을 담고 있습니다.

```cpp
// Source/Sonheim/GameObject/Items/BaseItem.h
USTRUCT(BlueprintType)
struct FItemSpawnOptions
{
	GENERATED_BODY()

	UPROPERTY(BlueprintReadWrite)
	bool bRequireInteraction = false; // 수동 상호작용 필요 여부

	UPROPERTY(BlueprintReadWrite)
	EItemInteractionType InteractionType = EItemInteractionType::Instant; // 즉시/홀드

	// ... and other dynamic properties (LifeTime, DropForce, etc.)
};
```

이러한 역할 분리는 데이터 주도 설계의 핵심적인 이점을 실현합니다. 만약 새로운 종류의 곡괭이(예: \'철 곡괭이\')를 추가하고 싶다면, 프로그래머는 `ABaseItem` 클래스를 건드릴 필요가 전혀 없습니다. 기획자는 단지 데이터 테이블에 아래와 같은 새로운 행을 추가하고, `ItemID`, `ItemName`, `ItemMesh` 등 정적 데이터만 채워 넣으면, 게임의 모든 시스템(제작, 인벤토리, 월드 드롭)이 즉시 \'철 곡괭이\'라는 새로운 아이템을 인식하고 처리할 수 있습니다. 이는 **수많은 아이템 블루프린트나 클래스를 만들 필요 없이**, 데이터만으로 콘텐츠를 무한히 확장할 수 있게 하는 데이터 주도 설계의 강력함을 보여줍니다.

```json
// 실제 Item.json 데이터 예시
{
    "Name": "pickaxe_stone",
    "ItemID": 110,
    "ItemCategory": "Equipment",
    "EquipmentData": {
        "SkillID": 111
    },
    "ItemName": "돌 곡괭이",
    "ItemIcon": "/Game/_Resource/.../T_itemicon_Weapon_Pickaxe_Tier_00.T_itemicon_Weapon_Pickaxe_Tier_00",
    "ItemMesh": "/Game/_Resource/.../SM_Pickaxe_01.SM_Pickaxe_01",
    "ItemRarity": "Uncommon"
}
```

#### 6.2.2.2.1. 스폰 옵션 템플릿: `MakeDropped` & `MakeInteractable`

`FItemSpawnOptions`는 많은 옵션을 가지고 있어 매번 수동으로 설정하기 번거롭고 실수를 유발할 수 있습니다. 이 문제를 해결하기 위해, 가장 자주 사용되는 두 가지 시나리오를 미리 템플릿화한 **인라인 헬퍼 함수**를 제공하여 개발 편의성을 극대화했습니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/GameObject/Items/BaseItem.h#L60)
```cpp
// Source/Sonheim/GameObject/Items/BaseItem.h

// 일반적인 자동 획득 아이템 (몬스터 드롭, 자원 채집 등)
inline FItemSpawnOptions MakeDropped(int32 Count, float Delay = 0.0f, ...)
{
	FItemSpawnOptions O;
	O.bRequireInteraction = false; // 자동 획득
	O.AutoPickupDelay = Delay;     // 획득 지연
	O.bApplyPhysicsOnDrop = true;  // 물리 효과 적용
    // ...
	return O;
}

// 플레이어가 직접 상호작용해야 하는 아이템 (퀘스트 아이템, 버린 아이템 등)
inline FItemSpawnOptions MakeInteractable(int32 Count, EItemInteractionType Type, ...)
{
	FItemSpawnOptions O;
	O.bRequireInteraction = true; // 수동 획득
	O.InteractionType = Type;     // 즉시 또는 홀드
    // ...
	return O;
}
```
이제 다른 시스템에서 아이템을 스폰할 때는, `MakeDropped(5)`와 같이 단 한 줄의 코드로 의도를 명확하게 표현하며 아이템을 생성할 수 있습니다.

### 6.2.2.3. 핵심 구현: 스폰 옵션에 따른 로직 분기

`InitializeItem` 함수는 주입받은 `FItemSpawnOptions`의 값에 따라, 아이템의 컴포넌트를 활성화하거나 타이머를 설정하는 등, 아이템의 동작 방식을 구체적으로 결정합니다.

#### 6.2.2.3.1. 상호작용 방식 분기

`InitializeItem` 내부에서 호출되는 `SetupComponents` 함수는 `bRequireInteraction` 플래그 값에 따라, 자동 획득에 사용되는 `CollectionSphere`의 오버랩 이벤트를 활성화할지, 아니면 비활성화하고 [[수동 상호작용|6.1_Unified_Interaction_System]]을 기다릴지를 결정합니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/GameObject/Items/BaseItem.cpp#L230)
```cpp
// Source/Sonheim/GameObject/Items/BaseItem.cpp
void ABaseItem::SetupComponents()
{
    // ...
    if (!bRequireInteraction)
    {
        // 자동 획득: Sphere Overlap 이벤트 활성화
        CollectionSphere->SetCollisionEnabled(ECollisionEnabled::QueryOnly);
        CollectionSphere->OnComponentBeginOverlap.AddDynamic(this, &ABaseItem::OnOverlapBegin);
    }
    else
    {
        // 수동 획득: Sphere Overlap 비활성화 (InteractInterface가 처리)
        CollectionSphere->SetCollisionEnabled(ECollisionEnabled::NoCollision);
    }
}
```

#### 6.2.2.3.2. 생명 주기 및 물리 효과 설정

`InitializeItem` 함수는 `LifeTime`과 `AutoPickupDelay` 값이 0보다 클 경우, 각각 `OnLifeTimeExpired`와 `EnableAutoPickup` 함수를 호출하는 타이머를 설정합니다. 또한 `bApplyPhysicsOnDrop`이 `true`이면, 아이템 메시에 `AddImpulse`를 가하여 드롭 연출을 만들어냅니다.

### 6.2.2.4. 회고 및 개선점: Net Dormancy를 이용한 네트워크 최적화

*   **문제:** 대규모 전투 후 수백 개의 아이템이 바닥에 드롭되었을 때, 모든 아이템이 계속해서 자신의 위치 정보를 서버와 클라이언트 간에 동기화한다면 심각한 네트워크 부하와 서버 성능 저하를 유발할 수 있습니다.
*   **해결 과정:** 언리얼 엔진의 **네트워크 도먼시(Net Dormancy)** 시스템을 도입했습니다. 아이템의 물리 시뮬레이션이 멈추는 `OnMeshSleep` 이벤트가 발생하면, 서버는 해당 아이템의 네트워크 상태를 `DORM_DormantAll`로 변경하여 모든 네트워크 업데이트를 중단시킵니다. 이후 플레이어나 다른 물리적 충격에 의해 아이템이 다시 깨어나는 `OnMeshWake` 이벤트가 발생하면, 즉시 네트워크 상태를 `DORM_Awake`로 되돌려 동기화를 재개합니다.
*   **교훈:** 대규모 멀티플레이어 환경에서는 눈에 보이지 않는 최적화가 매우 중요합니다. 엔진이 제공하는 저수준의 최적화 기능(Net Dormancy 등)을 깊이 이해하고 적극적으로 활용하는 것이, 직접 복잡한 시스템을 구현하는 것보다 훨씬 효율적이고 안정적인 결과를 가져온다는 것을 배웠습니다.

> [View on GitHub](https://github.com/chungheonLee0325/Sonheim/blob/main/Sonheim/Source/Sonheim/GameObject/Items/BaseItem.cpp#L263)
```cpp
// Source/Sonheim/GameObject/Items/BaseItem.cpp
void ABaseItem::OnMeshSleep(UPrimitiveComponent* Comp, FName)
{
    if (!HasAuthority()) return;

    // 움직임이 멈추면, 네트워크 업데이트를 완전히 중단하여 부하를 없앤다.
    SetNetDormancy(DORM_DormantAll);
}

void ABaseItem::OnMeshWake(UPrimitiveComponent* Comp, FName)
{
    if (!HasAuthority()) return;

    // 다시 움직이면, 즉시 네트워크 업데이트를 재개한다.
    FlushNetDormancy();
    SetNetDormancy(DORM_Awake);
}
```
